Why Your KPI Tracker Shows Two Numbers for the Same Thing

Quick answer. A KPI tracker is a Power BI report that pulls your core metrics from one clean data model and refreshes on a schedule. A good KPI tracker shows five to nine numbers, each defined as a single DAX measure, so every figure reads the same for everyone and can be checked on the spot. --- Most teams get their KPI tracker wrong, and it shows up in the first board meeting of the quarter. Two managers open the same view, see two different revenue numbers, and the rest of the meeting turns into an argument about which figure counts. Nobody talks about the business anymore. They talk about the data.

The problem is almost never the colors or the chart types. It sits underneath, in the data model. This article walks through why the numbers drift apart and the exact steps in Power BI that fix it, using a small sales example you can copy today.

Why does your KPI tracker show different numbers to different people?

The usual cause is a flat table. A lot of trackers start life as one big Excel export where revenue, region, product, and date all live in the same wide sheet. The moment you filter it, Power BI counts some rows twice, because the same order shows up on several lines. Your totals jump around depending on which slicer someone clicked.

The second cause is a missing definition. When "revenue" means the gross value on one tile and the after-discount value on another, every card calculates something slightly different. That gap matters more than it looks. About 94% of business spreadsheets used in decision-making contain errors (Poon et al., 2024). A tracker built straight on top of those sheets inherits every one of them.

The third cause is trust. 67% of organizations do not fully trust the data they use to make decisions (Precisely and Drexel LeBow, 2025). Once your board has corrected the number on the first tile, they stop believing the second tile too.

What is actually going wrong under the hood?

Take a sales team with an orders export. Each row is one order line: order ID, customer, product, region, order date, ship date, and amount. When you drop "amount" onto a card, you get the right grand total. Then someone adds a customer filter, and the number changes in a way nobody can explain.

Here is the mechanism. Because customer and region sit in the same table as the amount, Power BI has no separate list of customers to filter cleanly against. It scans the fact rows directly, and any repeated value throws the count off. You need a proper structure so the filtering flows one way, from a short list of customers into the long list of order lines.

How do you build the measures behind a KPI tracker?

Start by splitting that one wide table into a star schema: a fact table for the order lines, and dimension tables for Customer, Product, Region, and Date. The fact table stores the events with numbers. The dimensions store the descriptive fields. You connect them with one-to-many relationships, so one customer points to many order lines.

Then define every number as a measure in DAX rather than a calculated column. A measure recalculates the instant it is shown and adapts to whatever filter is applied. People often type "PowerBI create measure" into a search box hoping for a shortcut, and the actual shortcut is this: write revenue once as `Revenue = SUM(Orders[Amount])`, then build margin on top of it as its own measure. Each number gets one definition, it lives in the model, and anyone who asks can see it.

Three things matter here: how you write each measure, when you use relationship DAX for date comparisons, and how it all rolls up into a business KPI dashboard your board can read in ten seconds.

How do you compare against last year without breaking the numbers?

Most trackers need "this period versus the same period last year." That comparison depends on a real calendar table, not the date column buried in your orders. Build a dedicated Date dimension, set it as the report's date table, and connect it to your fact table.

A tricky case comes up when your fact table carries two dates, like order date and ship date. You can only have one active relationship to the calendar at a time. For the second one, you keep an inactive relationship and switch it on inside a specific measure with the USERELATIONSHIP function. So revenue by order date uses the active link, and revenue by ship date calls `CALCULATE(SUM(Orders[Amount]), USERELATIONSHIP(Orders[ShipDate], 'Date'[Date]))`. One fact table serves both views cleanly, and you never duplicate the data.

How do you keep a KPI tracker fast and trustworthy?

A tracker that was right yesterday is worthless today if nobody refreshes it. In Power BI you schedule the refresh: up to eight times a day on a Pro license, far more on capacity.

For large fact tables, turn on incremental refresh. You set two parameters, RangeStart and RangeEnd, and Power BI loads only the new rows instead of pulling the whole history every time. A refresh that took an hour can drop to a couple of minutes.

To keep people from seeing numbers that are not theirs, set up row-level security. A regional manager then sees only her region. Before you publish, test it with the "View As" feature so no figure lands in front of the wrong person. And separate your environments with deployment pipelines, which move changes from development to test to production without touching the live version. Poor data quality already costs organizations $12.9M per year on average (Gartner), and most of that comes from numbers nobody can trace.

How do you build your first KPI tracker, step by step?

You can do all of this today:

  1. Split your wide table into a fact table plus dimensions for Customer, Product, Date, and Region.
  2. Build a dedicated calendar table and connect it through one-to-many relationships, then mark it as the date table.
  3. In Power Query, add your cleanup steps so the raw data corrects itself on every refresh.
  4. Write each number as a DAX measure with one documented definition, and use USERELATIONSHIP for any second date.
  5. Pick at most nine numbers for the main view and turn on incremental refresh with RangeStart and RangeEnd.
  6. Test with "View As," set row-level security, and publish through a deployment pipeline.

Frequently asked questions

What is a KPI tracker, exactly? A KPI tracker is a report that pulls your most important numbers from a checked data model and refreshes them automatically. Each number has one fixed definition, so everyone in the room is talking about the same metric.

Do I need a star schema, or is one table enough? For two or three numbers, one table is fine. As soon as you filter by region, product, and time, you need a star schema, or Power BI double-counts rows and your totals jump.

Why use a measure instead of a calculated column? Because a measure calculates at the moment of display and respects every filter, so it stays correct in any slice. A calculated column is fixed when the data loads and cannot react to a slicer.

How do I compare this year to last year in a KPI tracker? Build a real calendar table and use time functions in DAX. When you have two dates like order and ship, keep the second relationship inactive and switch it on with USERELATIONSHIP inside the measure.

How often should a KPI tracker refresh? It depends on the decision. A board report is often fine on a daily refresh, while sales might want hourly. A Pro license allows up to eight scheduled refreshes a day.

Who should define the numbers? The business team decides what a number should mean, and the model locks that one definition in place. That turns a gut figure into something you can prove.
