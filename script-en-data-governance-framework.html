[0:55-2:40] VALUE BEAT 1 (workspace structure, the container)

(MODALITY: screen-record, live Power BI service)

CLAIM (on-screen text card): > A governance framework starts with where reports are allowed to live.

PROOF (screen-record the real thing): > This is a real tenant before we touched it. Forty-one workspaces, named "Sales", "Sales new", "Sales 2024 FINAL", and personal My Workspaces full of production reports the whole company depends on. Nobody can tell what's a draft and what's trusted. Here's the structure we put in. One workspace per business domain, finance, sales, operations, and inside each domain three stages: develop, test, and a locked production workspace where only a certified report gets published. Editors work in develop. Viewers only ever see production. I set that up here with workspace roles, Admin, Member, Contributor, Viewer, so a viewer can read the report but can't republish over it.

(ON-SCREEN: before/after card, messy 41-workspace list on the left, clean "Finance / Sales / Ops, each with Dev, Test, Prod" grid on the right)

PAYOFF (numbered takeaway card): > Takeaway one: one workspace per domain, three stages inside it, and production is publish-only for a small named group. That single structure ends My-Workspace production reports on day one.

RE-HOOK: > Structure gives reports an address. It still doesn't say who answers when one stops refreshing, so that's next.

[2:40-4:25] VALUE BEAT 2 (ownership, the refresh reliability layer)

(MODALITY: custom animation)

CLAIM (on-screen text card): > A dataset with no named owner is a dataset nobody repairs when the refresh stops.

PROOF (custom animation of the mechanism): > Watch the pattern that produces most of those red refreshes. Someone builds a dataset, wires the scheduled refresh to their own login, then changes team or leaves. The refresh keeps running on their credential. Weeks later that account gets disabled, the refresh goes red, and the report serves last month's numbers with no warning. An exec makes a call on stale data. The fix is two fields. Every certified dataset gets a named owner, a real person accountable for it, and the refresh runs on a service account, never a human login, so it survives anyone leaving.

(ANIMATION SPEC: a dataset box with an empty "Owner" field and a scheduled-refresh clock. A credential token attached to a person icon expires and greys out; the refresh status flips to red; the report tile keeps showing old figures with a small amber "stale" marker. Then rewind: the "Owner" field fills with a name, the credential swaps to a "service account" badge that stays lit as the person icon leaves, and the refresh status stays green. Amber is status only, per brand.)

PAYOFF (numbered takeaway card): > Takeaway two: name an owner on every certified dataset and move its refresh onto a service account. Do only this and your red-refresh count drops the same week.

RE-HOOK: > Owned and refreshing. Now the part that turns a plain report into the one people are told to trust.

[4:25-6:15] VALUE BEAT 3 (certification and endorsement)

(MODALITY: screen-record, Power BI service + admin portal)

CLAIM (on-screen text card): > Endorsement is how the trusted report gets a visible label instead of a rumour.

PROOF (screen-record): > Power BI has two endorsement levels built in and most teams use neither. Here's a dataset's settings. I can mark it Promoted, which any contributor can do, meaning "this is ready to share". Above that's Certified, the gold badge, which says "this is the official one". Now the open loop from the start. Go into the admin portal, Tenant settings, Certification. By default, certification is either off or open to the whole org, so anyone can stamp their own report Certified and the badge means nothing. Here's the real setup: turn certification on, but restrict who can certify to one named security group, your data owners. Add a link in that same box to your one-page certification checklist, so a badge always means the same thing.

(ON-SCREEN: two-tier card "Promoted (anyone) vs Certified (owners only)", then a zoom-punch on the admin "restrict to security group" field being switched from the whole org to "Data Owners")

PAYOFF (numbered takeaway card): > Takeaway three: turn on Certified, lock who can apply it to your data-owners group, and tie it to a written checklist. The label is only worth something when it's scarce and it means one thing.

RE-HOOK: > Now the badge points at a trusted report. It still won't help if every report defines revenue differently, so here's the piece that fixes that.

[6:15-8:05] VALUE BEAT 4 (one certified semantic model)

(MODALITY: custom animation)

CLAIM (on-screen text card): > One certified semantic model is what gets every report, and Copilot, to the same number.

PROOF (custom animation of the mechanism): > Here's what goes wrong without it. Three teams each write their own measure named Revenue. Finance counts it net of refunds, sales counts it gross at order date, marketing double-counts renewals. Same month, three totals, 1.2 million, 1.5 and 1.35, and every one gets defended. The framework answer is a single certified semantic model. You build the star schema once, a fact table in the middle, dimensions like Date, Product, Customer joined around it, and you write each headline measure one time, inside that model. Every report connects to it instead of rolling its own. And this is the part that matters for 2026: only 12 percent of organizations say their data is good enough to use for AI. Copilot reads your semantic model. One agreed model is also what makes Copilot answer correctly instead of guessing.

(ANIMATION SPEC: three file cards, each expanding a different "Revenue" DAX formula, three counters ticking to three totals, a shared "Revenue" label pulsing amber as a conflict marker. Then the three merge into one central certified semantic model box with a green badge; a star schema forms inside it, fact table centre, dimension tables snapping in with one-to-many arrows lighting up. Many report tiles and a small Copilot icon all connect to that one model with clean arrows. Amber status only.)

PAYOFF (numbered takeaway card): > Takeaway four: build one certified semantic model, write each headline measure once inside it, and point every report and Copilot at that model. One number, one owner, one source for the AI too.

RE-HOOK: > One model, one number. Now the two things the auditor asks for: who can see it, and can you prove who did.

[8:05-10:00] VALUE BEAT 5 (access and audit, the compliance layer)

(MODALITY: screen-record, with a short embedded RLS animation)

CLAIM (on-screen text card): > A framework isn't done until access is restricted and every action is on record.

PROOF (screen-record plus embedded animation): > Two things close the audit gap. First, access. This regional P&L should show each manager only their own region. I add a role in the model, write one filter, region equals the user's region using USERPRINCIPALNAME, and now the same report shows this manager three rows and that manager three different rows. Same file, filtered per person. On top of that I add a sensitivity label, Confidential, so the data stays protected even after someone exports it to Excel. Second, proof. This is the Purview audit log and the lineage view. Lineage shows exactly which source feeds which dataset feeds which report, so when an auditor asks where a number comes from, you point at a diagram. The audit log shows who viewed, shared, or changed a certified dataset, and when. That record is the difference between passing an audit and guessing.

(ANIMATION SPEC: reuse the standing RLS animation. One report, two user identities on the left; as each is selected, the table rows filter down to only that user's region. A sensitivity-label pill "Confidential" attaches to the exported Excel icon and stays attached. Then a lineage strip animates: Source to Dataset to Report as connected nodes lighting left to right, with an audit-log line ticking entries "viewed / shared / certified" beside it.)

PAYOFF (numbered takeaway card): > Takeaway five: row-level security on anything sensitive, a sensitivity label that travels with the data, and lineage plus the audit log so you can answer where a number came from and who touched it.

RE-HOOK: > That's all five parts built. Here's how they fit into a framework you can put on one page and start Monday.

Column two, standards: one certified semantic model, each headline measure defined once, and the Certified badge locked to your data-owners group with a written checklist behind it. Column three, access and audit: row-level security and sensitivity labels on anything sensitive, plus lineage and the audit log for proof.

It never meant anything because everyone could apply it. Restrict it to your owners and the badge does its job.
