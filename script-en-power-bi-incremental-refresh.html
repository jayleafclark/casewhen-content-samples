[1:20-3:05] VALUE BEAT 1 - what incremental refresh is doing (MODALITY: on-screen text - CLAIM card) (ON-SCREEN: "Incremental refresh splits your table into date partitions and only reprocesses the recent ones.") Austin: "Here's the whole idea in one sentence. Incremental refresh cuts your big table into slices by date, and on each refresh it only reprocesses the newest slices." (MODALITY: custom animation) (ANIMATION: the "incremental refresh partitions" library asset. A wide fact table, 20 million rows, splits into vertical partitions labelled by year and then by day: 2021, 2022, 2023, 2024, then Jan, Feb... down to the last 10 days. On the FIRST refresh, every partition lights up in #1D967C and processes once. On the SECOND refresh, the old partitions go grey and cold and stay untouched. Only the last 10 daily partitions light up and reprocess. A counter shows "Rows read: 20,000,000" on a full reload, then drops to "Rows read: 60,000" on the incremental run.) Austin: "First refresh, Power BI loads everything once and builds the partitions. That one's slow, and that's expected. Every refresh after that, the archive partitions sit cold. Power BI never touches them again. It only reads the last few days, so instead of 20 million rows it reads 60 thousand. Same report, a fraction of the work." (MODALITY: on-screen text - PAYOFF takeaway) (ON-SCREEN: "TAKEAWAY 1 - Old data doesn't change, so stop reloading it. Reprocess only recent partitions.") Austin: "So takeaway one. Last year's sales are done. They don't change. There's no reason to read them again, and incremental refresh is how you tell Power BI to leave them alone." Austin: "But Power BI won't just guess which rows are recent. You have to hand it two dates. Here's how that works."

[3:05-4:50] VALUE BEAT 2 - why it needs RangeStart and RangeEnd (MODALITY: screen-record - Power Query editor, Manage Parameters dialog, creating RangeStart and RangeEnd as Date/Time) (ON-SCREEN: "CLAIM - Two datetime parameters, RangeStart and RangeEnd, tell Power BI which window to load.") Austin: "Incremental refresh runs on two parameters with exact names. RangeStart and RangeEnd, both Date/Time. You create them in Power Query, then you filter your date column to sit between them. That filter is the whole trick." (MODALITY: custom animation) (ANIMATION: query-folding animation. Left: the Power BI semantic model box. Right: a source database cylinder. A filter chip "OrderDate >= RangeStart AND OrderDate < RangeEnd" starts inside Power BI. In the GOOD path it slides DOWN into the database and rewrites as a SQL WHERE clause; the database returns only the matching rows, a thin stream. In the BAD path the filter stays stuck inside Power BI; the database sends the ENTIRE table up the wire, a fat stream, and Power BI filters after the fact. Label the good path "Query folding ON", the bad path "Query folding OFF - still reads everything".) Austin: "When your source can fold, and that's SQL Server, Azure SQL, Synapse, most proper databases, Power BI pushes that date filter all the way down to the source as a WHERE clause. The database sends back only the recent rows. That's what makes it fast. When the source can't fold, the filter runs inside Power BI after it's already pulled the whole table. You get partitions, but you still read everything. Query folding is the part that does the actual saving." (MODALITY: on-screen text - PAYOFF takeaway) (ON-SCREEN: "TAKEAWAY 2 - No query folding, no real speed-up. Check View Native Query on your last step.") Austin: "Takeaway two. Before you trust incremental refresh, right-click your last step in Power Query and look for View Native Query. If it's greyed out, folding stopped somewhere, and you need to find where. That one check saves people days." Austin: "Alright. Parameters and folding sorted. Now let's really switch it on."

[4:50-6:55] VALUE BEAT 3 - setting it up step by step (MODALITY: screen-record - full walk-through in Power BI Desktop) (ON-SCREEN: "CLAIM - Setup is four steps: parameters, filter, policy, publish.") Austin: "Four steps, start to finish. Watch the screen." (SCREEN-RECORD, step 1) (ON-SCREEN callout: "1. Create RangeStart + RangeEnd (Date/Time)") Austin: "One. In Power Query, Manage Parameters, create RangeStart and RangeEnd as Date/Time. Give them any sensible default a year or two apart." (SCREEN-RECORD, step 2) (ON-SCREEN callout: "2. Filter your date column between them") Austin: "Two. On your fact table, filter the date column: is after or equal to RangeStart, and is before RangeEnd. Greater-than-or-equal on the start, strictly-less-than on the end, so no row lands in two partitions." (SCREEN-RECORD, step 3) (ON-SCREEN callout: "3. Right-click the table -> Incremental refresh") Austin: "Three. Close and apply. Right-click the table in the model, pick Incremental refresh, and set two numbers. Archive data starting, say, five years before refresh date. And refresh rows in the last, say, ten days." (MODALITY: custom animation) (ANIMATION: reuse the partition animation but now with a slider UI. Dragging "Archive: 5 years" widens the grey cold zone; dragging "Incrementally refresh: 10 days" widens the green hot zone at the right edge. Show the two policies stacking: a long grey ARCHIVE band and a short green REFRESH band.) Austin: "Those two settings are the whole policy. The archive number is how much history you keep. The refresh number is how far back you reprocess each run. Keep the refresh window a little wider than your late-arriving data, so nothing gets missed." (SCREEN-RECORD, step 4) (ON-SCREEN callout: "4. Publish to the Service - it only works there") Austin: "Four, and this is the one people miss. Publish to the Power BI Service. Incremental refresh doesn't run in Desktop. The first refresh in the Service builds every partition and it's slow, once. After that, every refresh is short." (MODALITY: on-screen text - PAYOFF takeaway) (ON-SCREEN: "TAKEAWAY 3 - Incremental refresh only runs in the Service, and the first refresh is a full load. That's normal.") Austin: "Takeaway three. Don't panic when the first Service refresh takes as long as your old one. That's it loading history once. Watch the second run instead." Austin: "So that's the clean setup on a database source. But a lot of you don't connect to a database. You connect to a dataflow. And that's where this goes wrong for a lot of teams."

[6:55-9:00] VALUE BEAT 4 - the dataflow re-import trap (pays off the open loop) (MODALITY: talking head, direct to camera, slower delivery on the problem line) (ON-SCREEN: lower-third "Semantic model -> dataflow -> re-imports EVERYTHING") Austin: "Here's the trap, and it's the most common one we get called in for. Your semantic model is connected to a Power BI dataflow, you set up incremental refresh on the model exactly like I just showed, and it still re-imports the entire dataflow on every run. Nothing got faster. This is that dataflow pain a lot of teams hit: the dataset connected to a dataflow isn't doing incremental refresh, it re-imports the whole dataflow every refresh." (MODALITY: custom animation) (ANIMATION: dataflow re-import asset. A semantic model box with a date filter chip tries to fold into a dataflow store. With enhanced compute engine OFF, the filter bounces off the dataflow and the entire dataflow contents flood into the model every refresh (fat stream, "reads everything"). Then a toggle flips: "Enhanced compute engine: On". Now the dataflow exposes a SQL-like endpoint, the date filter folds into it, and only recent rows stream through (thin stream). Caption: "Folding only works if the dataflow can be queried.") Austin: "Standard Gen1 dataflows don't support query folding by default, so that RangeStart-RangeEnd filter has nowhere to fold into. The fix is the enhanced compute engine. On a Premium or Fabric capacity, open the dataflow settings and set the enhanced compute engine to On. That gives the dataflow a queryable endpoint the filter can fold into, and now your model's incremental refresh pulls only recent rows. Better still, turn on incremental refresh on the dataflow itself too, so the dataflow only recomputes recent partitions before your model even asks." (MODALITY: on-screen text - PAYOFF takeaway) (ON-SCREEN: "TAKEAWAY 4 - Dataflow source? Turn ON the enhanced compute engine, or folding can't happen and you reload everything.") Austin: "Takeaway four, and this pays off the open loop from the start. If your source is a dataflow, incremental refresh on the model alone does nothing. Turn on the enhanced compute engine on the dataflow first. That's the one setting." Austin: "Now, even with folding working, you can go one step further and refresh less. Let me show you how."

[9:00-10:35] VALUE BEAT 5 - detect data changes (MODALITY: screen-record - the Incremental refresh dialog, ticking "Detect data changes" and picking a column) (ON-SCREEN: "CLAIM - Detect data changes skips partitions where nothing changed.") Austin: "By default, incremental refresh reprocesses every partition in your refresh window, even the days where nothing moved. Detect data changes fixes that. You point it at a last-modified column, and Power BI only reprocesses a day's partition if a row in that day really changed." (MODALITY: custom animation) (ANIMATION: partition strip of the last 10 days. Each day-partition carries a small "max ModifiedDate" stamp. Power BI compares the stored stamp to the current one. Eight days are unchanged and stay grey. Two days have a newer stamp and light up green and reprocess. Caption: "10 days in the window -> only 2 partitions really run.") Austin: "Say your refresh window is ten days but data only landed for two of them. Without this, you reprocess all ten. With detect data changes on a ModifiedDate column, Power BI checks the newest timestamp in each day, sees eight days are unchanged, and skips them. It only runs the two that moved." (MODALITY: on-screen text - PAYOFF takeaway) (ON-SCREEN: "TAKEAWAY 5 - Add a reliable last-modified column and enable Detect data changes to reprocess even less.") Austin: "Takeaway five. If your source has a trustworthy last-modified timestamp, use it. Detect data changes turns a ten-day refresh into a two-day refresh on quiet days. Just make sure that column is reliable, because Power BI trusts it completely." Austin: "Good. It's set up and it's lean. Now, how do you know it's really working and not just looking like it?"

[10:35-12:05] WORKED EXAMPLE / REAL NUMBER - proving it worked (MODALITY: data-viz - animated before/after bar) (ON-SCREEN: before/after bars "Refresh time: 47 min -> 4 min") Austin: "Here's a real one from an engagement. A sales model, about 30 million rows, refreshing in 47 minutes twice a day and regularly timing out. We put RangeStart and RangeEnd on the order date, archived five years, refreshed the last 14 days, and fixed the folding on the source. Refresh dropped to 4 minutes. Same data, same report, one change to how it loads." (MODALITY: screen-record - SSMS connected to the XMLA endpoint, expanding the table to show individual dated partitions; then the Service refresh history showing the short durations) (ON-SCREEN callout: "Proof 1: partitions exist. Proof 2: refresh history got short and stayed short.") Austin: "Two ways to prove it for yourself. One, connect to the XMLA endpoint with SQL Server Management Studio on Premium or Fabric, expand the table, and you'll see the actual dated partitions. If they're there, partitioning worked. Two, and simpler, open the refresh history in the Service. Your first run is long, then every run after drops and stays down. If the second refresh is still as long as the first, folding didn't happen, and you go back to View Native Query to find where it stopped." (MODALITY: on-screen text) (ON-SCREEN: "If refresh #2 isn't shorter than #1 -> folding broke. Recheck View Native Query.") Austin: "That second-refresh check is your whole test. Short second run, you're done. Long second run, folding broke somewhere in your query steps."

[12:05-14:00] PAYOFF RECAP + SOFT CTA (MODALITY: on-screen text - kinetic list, all five takeaways stack in) (ON-SCREEN: "1. Stop reloading old data. Reprocess only recent partitions. 2. No query folding, no speed-up. Check View Native Query. 3. It only runs in the Service. First refresh is a full load. 4. Dataflow source? Turn ON the enhanced compute engine. 5. Reliable last-modified column? Enable Detect data changes.") Austin: "So there's the whole thing. One, stop reloading old data. Two, no query folding means no real speed-up, so check View Native Query. Three, it only runs in the Service and the first refresh loads everything once. Four, if you're on a dataflow, turn on the enhanced compute engine or nothing folds. And five, add a reliable last-modified column and switch on detect data changes to refresh even less." (MODALITY: talking head) Austin: "And the open loop from the start, that one dataflow setting, is number four. The enhanced compute engine. It's the thing that makes people blame incremental refresh when the dataflow was the cause all along. Turn it on and the whole thing clicks into place."
