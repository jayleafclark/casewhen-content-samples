A Real Look at Power BI Incremental Refresh (Not a Checklist)

Power BI incremental refresh is a setting that reloads only the newest rows of a large table instead of the whole thing every time. You define two parameters, RangeStart and RangeEnd, set a policy for how far back to store data and how recent to refresh, and Power BI splits the table into date partitions so the daily refresh stays small and quick. ---

Most teams set up a big dataset once, forget about the Power BI incremental refresh option, and then wonder why the morning refresh crawls while everyone waits for the sales report to load.

If your refresh started at two minutes and now takes forty, this is almost always the cause. The table grew, and Power BI is reloading all of it, every single day, even the rows that have not moved in three years.

The fix is a built-in feature. It works on a Power BI Pro plan (not just Premium), and you can set it up this afternoon. The rest of this post covers what it does, why refreshes get slow, and the exact steps to turn it on.

Why does your morning refresh keep getting slower?

By default, every scheduled refresh does a full reload. Say your sales table has five years of orders and grows by 50,000 rows a day. On a full reload, Power BI throws away all 90 million rows and pulls every one of them back from the source. Only yesterday's data is new. The other five years are identical to what you had before.

That waste is the whole problem. As the table grows, the refresh window grows with it. A dataset that refreshed in two minutes last year now needs forty, and if it crosses your capacity's time limit, it stops before it finishes.

There is a second reason this bites hard, and it has nothing to do with size. When a report takes too long to open, people stop opening it. They go back to the spreadsheet on their desktop. That matters, because 67% of organizations already don't fully trust the data they use to make decisions (Drexel LeBow and Precisely, 2025). A report that is slow or stale feeds that distrust.

How does power bi incremental refresh really work?

The idea is simple. Instead of one giant table, Power BI stores your data in dated slices called partitions, usually one per day or one per month. A refresh only touches the recent partitions. The old ones sit untouched.

Two parameters draw the boundary. RangeStart marks the earliest date in the window you want to load, and RangeEnd marks the latest. You filter your date column to keep only rows between them. Power BI reads that filter and uses it to build and refresh each partition.

Then you set two windows in the policy:

  • Store rows from the past: how much history to keep. For example, 5 years.
  • Refresh rows from the past: how recent a slice to reload each time. For example, 10 days.

With those numbers, Power BI keeps five years of orders but only reloads the last ten days on each refresh. Everything older is frozen. The refresh that took forty minutes now takes under two, because it is pulling ten days of rows instead of five years.

How do you set up incremental refresh step by step?

Here are the exact steps. You do all of this in Power BI Desktop, then publish.

  1. Open Power Query (Transform data) and create two parameters named exactly RangeStart and RangeEnd. Set both to the Date/Time type. The names matter and are case sensitive.
  2. On your fact table, filter the date column to keep rows where the date is after or equal to RangeStart and before RangeEnd. This is the filter Power BI uses to slice the table.
  3. Close Power Query. In report view, right-click the table in the Data pane and choose Incremental refresh.
  4. Toggle it on, then set Store rows from the past (say, 5 years) and Refresh rows from the past (say, 10 days).
  5. Turn on Only refresh complete days so a half-finished day never loads mid-way and shows wrong totals.
  6. Turn on Detect data changes and point it at a "last modified" column if your source has one. Power BI then reloads a day only when a row in it changed, which shrinks the refresh even more.
  7. Publish to the Power BI service. The first cloud refresh builds all the partitions and runs long once. Every refresh after that is small and fast.

One catch that trips people up: this only helps if the query folds. Query folding means Power BI can push your date filter down to the source database as a WHERE clause. If your source is a folder of CSV files or a step that breaks folding, Power BI cannot ask for "just the last ten days," so it reads everything anyway. Check folding by right-clicking your last query step and looking for View Native Query. If that option is greyed out, fix the folding before you count on incremental refresh.

What does incremental refresh have to do with power bi security?

More than most people expect, because both live inside the same semantic model. Once you have partitions, you want to know who can trigger a refresh, whose credentials the scheduled refresh uses, and whether a change to the policy got reviewed. This is where power bi security and refresh design meet.

A few practical points. The security Power BI applies through row-level roles still runs on top of your partitions, so filtering data by region or client works the same before and after you turn on incremental refresh. The refresh history in the service shows every run, its duration, and whether it finished, which is your first stop when a number looks stale. And the audit log records who published a new model version, so a change to the "store 5 years" number leaves a trace someone can review.

The point is to write this down. A short data governance structure that names the dataset owner, the refresh schedule, the store and refresh windows, and who signs off on changes turns a fragile setup into one your team can maintain without you. When the person who built the model leaves, the next person reads the doc instead of guessing.

When should you not use incremental refresh?

Setting this up takes effort, so skip it when the payoff is small.

  • Tiny tables. If a table has under a million rows and refreshes in seconds, the setup work is not worth it. Leave it on full refresh.
  • Sources that cannot fold. If your date filter cannot reach the source as a real query, Power BI reads the whole table anyway, and you get the complexity with none of the speed.
  • Data that changes deep in history. If someone edits orders from two years ago and you must catch every edit, frozen partitions will miss them unless you use Detect data changes carefully or reload manually.
  • Real-time needs. If people need data that is seconds old, incremental refresh on an import model is the wrong tool. Look at DirectQuery or a Direct Lake model on Fabric instead.

For everything else, a fact table that grows every day and carries years of history, this is the single change that keeps refreshes fast for years.

Frequently asked questions

Does power bi incremental refresh need Premium? No. It has worked on a Power BI Pro license since February 2020. Premium and Premium Per User add extras like larger models and XMLA endpoint access, but the core feature runs on Pro.

Why did my refresh time not improve after I turned it on? Almost always query folding. If Power BI cannot push the RangeStart and RangeEnd filter to the source, it reads the full table regardless of the policy. Right-click your final query step and confirm View Native Query is available.

Will I lose my old data? No. The "store rows from the past" window controls how much history stays in the model. Set it to five years and you keep five years. Only the "refresh rows from the past" window is reloaded each run.

Can I refresh a single old partition after a data fix? Yes, through the XMLA endpoint with a tool like SQL Server Management Studio or Tabular Editor, which lets you refresh one partition on demand. This needs Premium or Premium Per User.

How does this affect row-level security? It does not change it. Your row-level roles filter the same way across all partitions, so power bi security behaves identically whether the table uses full or incremental refresh.

Should the refresh policy live in our governance docs? Yes. Record the owner, the store and refresh windows, and the review step in your data governance structure so the setup survives staff changes and stays auditable.
