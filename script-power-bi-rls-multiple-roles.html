CLAIM (on-screen text card): "Static RLS hard-codes who sees what. Dynamic RLS looks up the logged-in user at run time."

[VALUE BEAT 2 · 2:10-3:45] Why do two roles show more data, not less? (MODALITY: data-viz)

CLAIM (on-screen text card): "When a user sits in two roles, Power BI adds the rows together. It never narrows them."

Then assign the same user to Role B "Leadership sees all", which returns all 40 rows. Animate the two filters combining with a union symbol, and show the result snap to 40 rows. PAYOFF (numbered takeaway card): "Takeaway 2: roles are permissive. A second role only ever grants more access. Assign each person to exactly one role, and let the DAX decide what they see."

RE-HOOK: "So you consolidate everyone down to one clean role. And now the report opens completely empty. That's a different problem with a different cause."

[VALUE BEAT 3 · 3:45-5:20] Why is my whole report suddenly empty? (MODALITY: screen-record)

CLAIM (on-screen text card): "A blank dynamic RLS report almost always means the user lookup matched nothing."

DEMO / SCREEN-RECORD: In Power BI Desktop, open Modeling, View as, tick the dynamic role. The report goes blank. Cut to the Users table and show the stored value: `jsmith@contoso.com`. Then drop a quick measure on the canvas, `= USERPRINCIPALNAME()`, and show what the Service sends back: `j.smith@contoso.com`. Call out the mismatch with a boxed label. Show three real causes side by side: the dot in the name, a `DOMAIN\jsmith` style login stored instead of the email, and a user who simply isn't in the Users table at all. Then fix it live: normalise the column to lowercase email, add the missing user, re-run View as, and the rows come back. (ON-SCREEN: red callout "stored: jsmith@ vs sent: j.smith@" then green "MATCH")

PAYOFF (numbered takeaway card): "Takeaway 3: store the exact UPN the Service sends, lowercase, one row per person. No matching row means no data, by design."

RE-HOOK: "Now the lookup matches. And the report is still empty, or still shows everything. The filter isn't reaching your sales numbers. That's the model."

[VALUE BEAT 5 · 7:00-9:00] How do I build one role that works? (MODALITY: screen-record)

[9:00-11:00] WORKED EXAMPLE: the leak and the test (MODALITY: b-roll then screen-record)

Spoken open (over b-roll): "This is the part most teams miss, and it's the reason a report passes in Desktop and leaks in production."

(MODALITY: b-roll) Two seconds of real footage: a BI analyst at a desk in the Berlin office, a second monitor with a dashboard, hands on keyboard. Then cut to screen.

(MODALITY: screen-record) Open the Users-to-Region relationship, go to the advanced properties, and show the checkbox "Apply security filter in both directions". Explain plainly: when the filter has to run from the security table up into a dimension and then down into the fact, this checkbox is what carries it across that middle join. Tick it on that one security relationship only. Then warn on screen: if you also have bidirectional cross-filtering switched on elsewhere in the model, the security filter can travel back out and surface rows for people who shouldn't see them. Keep every other relationship single-direction, and use this checkbox only on the relationship that connects the security table.

Then the test. Modeling, View as, choose "Other user", type a real UPN like `j.smith@contoso.com`, and confirm the report shows exactly one region. Publish to the Service, then sign in as a genuine second account and confirm the same result there, because Desktop uses your own login unless you supply "Other user". (ON-SCREEN: before/after figure. "Before: role returns all 40 rows (leak) OR 0 rows (blank)" flips to "After: exactly 4 rows, one region". Callout on the checkbox: "security relationship only")

Spoken close: "That's the open loop from the start. The checkbox that makes dynamic RLS work is the same one that can open a hole, so you switch it on in one place and leave the rest of the model single-direction."

Dynamic row-level security in Power BI breaks for a short list of reasons. Multiple roles combine with OR, so a second role grants more access instead of narrowing it. A blank report usually means USERPRINCIPALNAME didn't match the value stored in your security table. And the filter often can't reach the fact table because the relationship path or cross-filter direction stops it. This walkthrough shows the static versus dynamic RLS difference, the multiple-roles trap, the empty-report fix, the relationship path that carries the filter, and a single dynamic role driven by USERPRINCIPALNAME that works in the Power BI Service.
