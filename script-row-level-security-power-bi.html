### [2:15-4:00] BEAT 2: How do I build static RLS with roles? (screen-record) CLAIM (on-screen card): "A static role is a fixed filter you write once, then assign people to." PROOF (MODALITY: screen-record, Power BI Desktop, real cursor): - Modeling tab, click Manage roles. - Create a role, call it "Nord". Pick the Region table. Write the DAX filter: [Region] = "Nord". - Create a second role "Sued" with [Region] = "Sued". Show the two roles listed. - Save, then Home, Publish to the Service. - Cut to the Service: open the dataset, Security, drop a user's email into the Nord role. (VISIBLE CHANGE ~6s: cursor zoom on the DAX box, then a callout box circling the Security assignment screen.) PAYOFF (on-screen numbered takeaway): "Takeaway 2: one role equals one filter. Build a role per group, then drop the right people into each role in the Service." RE-HOOK: "That's clean for four regions. Now picture four hundred sales reps →"

### [4:00-5:30] BEAT 3: Why does one role per person fall apart? (animation) CLAIM (on-screen card): "A role per person doesn't scale, and it rots the day someone changes teams." PROOF (MODALITY: custom animation): - Three role cards on screen. They multiply, 3 to 30 to 300, each card needing a manual hand-assignment in the Service. The pile gets visibly unmanageable. - One person icon moves from Nord to Sued. A red tag pops: "manual edit needed". Then a second red tag: "who owns this?". - Cut to a single card labelled "Dynamic role" that reads from a small table. One card, green. PAYOFF (on-screen numbered takeaway): "Takeaway 3: if you're writing a role per person, stop. You want one role that looks up the user while the report runs." RE-HOOK: "That lookup is one function, and it's already in your model →"

### [5:30-7:30] BEAT 4: How do I make it dynamic with USERPRINCIPALNAME? (screen-record) CLAIM (on-screen card): "Dynamic RLS uses the logged-in email to filter, from a small mapping table." PROOF (MODALITY: screen-record, Power BI Desktop): - Show a mapping table called UserRegion with two columns: UserEmail and Region. A few rows of real-looking emails mapped to Nord, Sued and so on. - Modeling, Manage roles. Create one role called "Dynamic". Filter the UserRegion table with: [UserEmail] = USERPRINCIPALNAME(). - Cut to Model view. Show the relationship going from UserRegion to the region column and on down to the Sales fact, so the filter flows one-to-many toward Sales. Show the arrow direction. - Publish. In the Service, assign every user to the single Dynamic role. (VISIBLE CHANGE ~6s: zoom on the USERPRINCIPALNAME() line, then a marker sweeping the relationship arrow in Model view.) PAYOFF (on-screen numbered takeaway): "Takeaway 4: one role, filter [UserEmail] = USERPRINCIPALNAME(), backed by a mapping table you update without opening the model. Add a person as a row and you're done." RE-HOOK: "This is also the exact spot where it silently leaks. Two ways →"

### [7:30-9:30] BEAT 5: Why is my RLS leaking or showing nothing? (data-viz) CLAIM (on-screen card): "Almost every RLS breakdown is a relationship direction or a missing mapping row." PROOF (MODALITY: animated data-viz / diagram, the two cases side by side): - Leak case: the relationship between UserRegion and the fact points the wrong way, so the filter never reaches Sales. The report shows every row for everyone. Show the arrow, then flip its direction, and watch the rows clamp down to the correct set. - Empty case: the logged-in email isn't in the UserRegion table. The filter matches zero rows and the whole report goes blank. Show the email miss, then the blank canvas, then add the row and the report fills back in. - Add the snowflake gotcha: on a longer dimension path the filter can stall one table short of the fact. Show it stopping, then reaching. PAYOFF (on-screen numbered takeaway): "Takeaway 5: if a report shows everything, the filter isn't reaching the fact table. If it shows nothing, the user's email is missing from the mapping. Those two cover most leaks." RE-HOOK: "Which is why you never ship RLS you haven't seen through the user's own eyes →"

### [9:30-11:15] BEAT 6: How do I test it before it ships? (screen-record) CLAIM (on-screen card): "View As lets you see the report as a role or as a specific person before anyone logs in." You're seeing exactly what they'll see. - Cut to the Service: dataset, Security, use "Test as role" on the same role to confirm it behaves live. (VISIBLE CHANGE ~5s: cursor zoom on the "Other user" field, then a side-by-side of two emails giving two row sets.) PAYOFF (on-screen numbered takeaway): "Takeaway 6: before you publish, View As every role and at least one real email per region. If the rows are wrong here, they're wrong in production." RE-HOOK: "Do that, and the two-login demo from the very start just works →"

This is a full row level security Power BI build, static and dynamic. Static RLS is a fixed filter written into a role and assigned to people in the Power BI Service. Dynamic RLS uses one role that filters a mapping table with USERPRINCIPALNAME(), so the logged-in email decides which rows show, with no role-per-person maintenance. We cover the two failures that cause most RLS leaks, a relationship that doesn't reach the fact table and an email missing from the mapping table, and how to catch them with View As before you publish. Works the same in Power BI and in a Fabric semantic model.
