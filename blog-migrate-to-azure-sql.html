Migrate To Azure SQL: What Actually Breaks (and How to Avoid It)

Quick answer: To migrate to Azure SQL, you assess the source database with Data Migration Assistant, pick a target (Azure SQL Database or Managed Instance), copy the schema and data using DMS, then cut over during a quiet window. Test SQL Agent jobs, linked servers, and connection retry logic first, because those are what usually break. ---

Most teams that migrate to Azure SQL get one thing wrong, and it shows up three weeks after cutover, when a nightly report that used to load in seconds times out at 6 a.m. The move itself went fine. The database is in the cloud, the data is all there, and the demo looked great. Then a scheduled job goes missing, a linked server stops answering, and a dashboard throws an error nobody can explain.

None of that is bad luck. It's the predictable part of the job that got skipped. This piece walks through what changes when you move a database from your own SQL Server to Azure SQL, why the usual surprises happen, and the exact order we run a migration so those surprises show up in testing instead of in production.

What actually changes when you move to Azure SQL?

Your old SQL Server was a whole machine you controlled. You had the operating environment, the file paths, the SQL Server Agent, and every database on the box able to talk to every other one. Azure SQL takes some of that away in exchange for Microsoft running the hardware, the patching, and the backups for you.

There are two main targets, and the gap between them is the first real decision.

Azure SQL Database is a single database in the cloud. It's the cheapest and most hands-off, but it drops features you may lean on: no SQL Server Agent, no cross-database queries by default, no linked servers, and no SQL Server-level logins. Each database mostly lives on its own.

Azure SQL Managed Instance is closer to the SQL Server you know. It keeps the Agent, cross-database queries, and most instance-level features, so more of your existing code moves over untouched. It costs more and takes longer to deploy.

Pricing works one of two ways. The DTU model bundles compute, memory, and I/O into one blended number, which is simple to start with. The vCore model lets you pick CPU cores and memory separately, and it's the one most teams settle on because you can size it to a real workload and use Azure Hybrid Benefit to reuse existing licenses.

Why do reports and jobs break after you migrate to Azure SQL?

Three things cause almost every post-migration surprise, and each one traces back to a feature that behaves differently in the cloud.

The first is scheduled jobs going quiet. If your source ran nightly loads through SQL Server Agent and you moved to Azure SQL Database, the Agent isn't there. Those jobs don't error out with a red flag. They simply never run, and the first sign is stale data on Monday morning. Managed Instance keeps the Agent, and Azure SQL Database has Elastic Jobs as the replacement, but only if you set it up on purpose.

The second is transient connection errors. A cloud database sits behind a gateway that can move your database to different hardware for maintenance or load balancing. When that happens you get a brief dropped connection with a code like 40197 or 40501. On a physical server this never happened, so a lot of older application code has no retry logic. The fix is to wrap connections in a retry pattern that waits and tries again, which most modern data libraries support with a single setting.

The third is cross-database and linked-server calls. A query that joins `SalesDB.dbo.Orders` to `FinanceDB.dbo.Ledger` works on one server because both databases share the machine. On Azure SQL Database they're isolated, so that query returns an error the moment it runs. You either move to Managed Instance, use elastic queries, or redesign so the data lives together.

What is the safest way to migrate to Azure SQL, step by step?

You don't guess your way through this. Here's the order we run, and the first two steps take an afternoon.

  1. Run Data Migration Assistant (DMA) first. This free Microsoft tool scans your source database and produces a report of exactly what won't move cleanly: unsupported features, deprecated syntax, and blocking issues. Read that report before you pick a target. It usually decides Database versus Managed Instance for you.
  2. Pick the target and tier. Use the DMA report plus a look at your Agent jobs and linked servers. If you have many of both, Managed Instance saves weeks of rewrites. Size the vCore tier to your busiest hour, not your average, so nothing throttles at month-end close.
  3. Move schema and data with Azure Database Migration Service (DMS). DMS handles the copy and can run in online mode, which keeps the source live while it syncs, so your cutover downtime shrinks to minutes. For smaller databases, a BACPAC export and import works fine.
  4. Rebuild the jobs and connections. Recreate every SQL Agent job as an Elastic Job (Database) or a normal Agent job (Managed Instance). Update every application connection string to the new server name, turn on encryption, and add retry logic for those transient codes.
  5. Test with real queries before cutover. Point a copy of your Power BI reports and your heaviest stored procedures at the new database. Watch the ones that use DirectQuery, because they now cross the internet to reach the data, and a chart that felt instant on the local network can lag. Set compatibility level to match the source, then raise it once things are stable.
  6. Cut over in a quiet window and keep the old server for a week. Do the final sync, switch connection strings, and run your smoke tests. Leave the source database read-only and reachable for a week so you have a fallback while confidence builds.

Do steps one through three and the data moves safely. Do four and five and the 6 a.m. surprises never reach production.

How do you avoid the most common migration mistakes?

The pattern behind most rough migrations is treating the copy as the whole job. The copy is the easy 20 percent.

Poor data quality costs organizations an average of $12.9M a year (Gartner), and a rushed migration is one of the fastest ways to add to that bill, because a job that silently stops running means every report downstream is now wrong without warning. Here is the short list of what teams skip, and what to do instead.

Common mistakeWhat it costs youThe fix
Assuming SQL Agent jobs come alongStale data, no error shownRebuild as Elastic Jobs or use Managed Instance

The through-line is simple. Every feature that depended on the old machine (the Agent, shared databases, always-on connections) needs a deliberate replacement, and each one gets tested before real users touch it.

Should you migrate SQL to Azure SQL, or stay where you are?

It's worth an honest test here, because not every database belongs in Azure SQL yet.

You're a good fit when you want Microsoft to handle patching and backups, when you need to scale compute up and down, or when the rest of your data platform (Power BI, Azure Data Factory, a Fabric workspace) already lives in Azure and you want the database next to it. The plan to migrate SQL to Azure SQL pays off fastest when it removes a server someone on your team is babysitting.

You should wait when your app depends on features Azure SQL still doesn't offer (certain cross-instance tricks, filestream, or heavy direct file access), or when a straight lift to a SQL Server virtual machine in Azure is the cheaper, lower-risk step for now. A SQL Server VM gives you the cloud address without changing the database engine, so it's often the bridge before a full move.

One more thing to plan around: a database migration rarely travels alone. If you're moving the data platform, the reporting layer usually moves at the same time, and a tableau to power bi migration on top of the database work is common enough that it's worth scoping both together instead of twice.

What does a clean Azure SQL migration hand back to you?

At the end you should have the new database serving every application, every scheduled job rebuilt and proven to run, retry logic in the connection layer, and a written record of what changed. You should also have your Power BI reports pointed at the new source and confirmed fast, plus the old server sitting read-only as a safety net until everyone trusts the new one.

If all you got was a copied database and a thumbs-up, the risky 80 percent is still ahead of you. A real migration is done when the boring parts (jobs, connections, report speed) are boring again.

Frequently asked questions

How long does it take to migrate to Azure SQL? A single, well-understood database with clean code and no exotic features often moves in two to four weeks, including testing. Databases with many SQL Agent jobs, linked servers, or legacy syntax take longer, mostly in the rebuild-and-test phase rather than the copy itself.

What's the difference between Azure SQL Database and Managed Instance? Azure SQL Database is a single, low-maintenance database that drops instance-level features like the SQL Server Agent and cross-database queries. Managed Instance keeps most of those features, so more of your existing code moves without changes. Pick Database for simple workloads and Managed Instance when you rely on Agent jobs or shared databases.

Will my application need code changes? Usually a few. You'll update connection strings, turn on encryption, and add retry logic for transient cloud errors. Apps that use linked servers or cross-database queries on Azure SQL Database need more rework, which is one reason the DMA scan matters before you commit.

Can I migrate SQL to Azure SQL with no downtime? Close to none. The DMS online mode syncs the source while it stays live, so the final cutover is a short switch measured in minutes, not hours. True zero downtime depends on your app tolerating a brief connection swap.

Do I have to move my reports too? You don't have to, but plan for it anyway. Power BI reports keep working once you update the data source, though DirectQuery reports may need a second look because they now reach the database over the internet. If you're also changing tools, scope the tableau to power bi migration alongside the database move so you test everything once.

Is a SQL Server VM in Azure ever the better choice? Yes, when you need full instance control or depend on features Azure SQL doesn't support. A SQL Server virtual machine gives you the cloud location without changing the engine, so it's a lower-risk first step you can build on later.
