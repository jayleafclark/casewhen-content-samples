Incremental Refresh Power BI, Explained With a Real Example

Quick answer. Incremental refresh Power BI is a setting that reloads only the rows that changed recently instead of the whole table. You partition a large table by a date column using RangeStart and RangeEnd, so a refresh that once took 45 minutes finishes in seconds and stops timing out overnight. --- You switched on incremental refresh Power BI to make your dataset reload faster, and the nightly refresh is still just as slow. Your sales table has 40 million rows. Every scheduled refresh reloads all 40 million of them, even though only yesterday's orders actually changed. A refresh that should take 30 seconds takes 45 minutes, and at 2am it times out before the report is ready for the 9am meeting.

That's the situation this article walks through. One real table, one slow refresh, and the exact settings that fix it. By the end you'll know what the feature does, how to turn it on correctly, and the one setting people miss that makes it look like it did nothing.

Why does a full refresh get so slow?

By default, a Power BI dataset does a full reload. Every time the refresh runs, it goes back to the source, pulls the entire table, and rebuilds it in memory from scratch. For a 5,000-row lookup table, nobody notices. For a 40-million-row fact table that grows every day, the refresh gets longer every month.

Two things go wrong at once. The refresh window in the Service has a time limit (2 hours on shared capacity), so a long refresh can hit that ceiling and stop. And your source database takes the full read every single time, which slows down other jobs that share it. The report is stale by morning, and the database team gets paged.

The fix is to stop reloading rows that haven't changed. Yesterday's orders are done. Last year's orders are really done. There's no reason to read them again tonight.

What's incremental refresh Power BI, in plain terms?

Incremental refresh Power BI splits one big table into many small date-based slices, called partitions, and only reloads the recent ones. Think of it like a filing cabinet with one drawer per month. Instead of emptying every drawer and refiling everything, you only touch this month's drawer.

You draw the line with two parameters, RangeStart and RangeEnd. Power BI uses them to decide which rows belong to which partition and which partitions are old enough to leave alone. You tell it two numbers: how far back to keep data at all (say 5 years), and how far back to actually refresh each run (say the last 10 days). Everything older than the refresh window is frozen and read once, then never again.

How do you set up incremental refresh step by step?

You do this once in Power BI Desktop, then publish. The steps below take about ten minutes.

  1. Create the two parameters. In Power Query, open Manage Parameters and add RangeStart and RangeEnd. Set the type to Date/Time. The exact names matter, because Power BI looks for them by name.
  2. Filter your fact table by date. On your big table, filter the date column so it's greater than or equal to RangeStart and less than RangeEnd. This one filter is what the whole feature keys off.
  3. Close and apply. Load the model back into Power BI Desktop.
  4. Open the policy. Right-click the table in the Data pane and choose Incremental refresh. Toggle it on.
  5. Set the two windows. Fill in "Archive data starting" with how much history to keep (for example, 5 years) and "Incrementally refresh data starting" with your refresh window (for example, 10 days).
  6. Publish and let the first refresh run. The first refresh in the Service is slow, because it builds every partition once. After that, each nightly refresh only touches the last 10 days.

There's one more toggle worth knowing: "Detect data changes." Point it at a last-modified datetime column, and Power BI checks the maximum value in each recent partition and skips the ones where nothing moved. On a table where old days occasionally get a correction, this saves another chunk of time.

Why is query folding the part people get wrong?

This is where a setup that looks correct still runs for 45 minutes. Incremental refresh only helps if the RangeStart and RangeEnd filter reaches the source as a SQL WHERE clause. That translation is called query folding. When it folds, the database returns only 10 days of rows. When it doesn't fold, Power BI pulls all 40 million rows into memory and then filters them, so you did all the work anyway and gained nothing.

Query folding breaks when a step in Power Query can't be turned into SQL. Common culprits are a custom column added too early, a merge with a non-foldable source, or reading from flat files instead of a database. To check, right-click the last step in Power Query and look for "View Native Query." If that option is greyed out on the step after your date filter, folding stopped, and you need to move or remove whatever broke it.

So the real test after you publish is simple: watch the second refresh, not the first. If it's still slow, folding is almost always the reason.

How does incremental refresh connect to governance and security?

A refresh that runs long or times out has a second cost beyond time. People stop trusting the number on the dashboard, and a report that's a day old feeds that doubt. This is a bigger deal than it sounds: 67% of organizations don't fully trust the data they use to make decisions (Precisely and Drexel LeBow, 2025). Reliable, on-time refreshes are one of the plain ways you earn that trust back.

Incremental refresh is one rung on the maturity model data governance teams climb. Right next to it sit access rules and change control. Row-level security, part of Power BI security, controls which rows each person sees, and it runs on top of the very tables incremental refresh partitions, so the two get designed together rather than bolted on later.

Change control matters too. When you promote a dataset from development to test to production with deployment pipelines, sometimes written Power BI pipelines, the incremental refresh policy travels with it. You set the policy once, and each stage keeps it, so nobody reconfigures partitions by hand in production and gets it slightly wrong.

When should you skip incremental refresh?

Incremental refresh takes some effort to maintain, so it earns its place only on tables that are both large and date-based. Skip it when:

  • The table is small. Under a million rows, a full refresh is already fast, and the extra setup adds complexity for no gain.
  • There's no reliable date column. Incremental refresh needs a datetime value that doesn't change for old rows. An order date works. A "last touched" field that shifts around doesn't.
  • You need true real-time. Incremental refresh runs on a schedule. For live streaming numbers, that's a different tool (DirectQuery or a real-time dataset).

For most growing fact tables in sales, finance, or operations, none of those apply, and the payoff is large. A nightly job that used to run 45 minutes and sometimes time out now finishes in under a minute and never touches old data again.

Frequently asked questions

Does incremental refresh work on Power BI Pro? Yes. Since 2020 it's available on Power BI Pro, not only on Premium. You don't need a premium capacity to get the refresh-time savings.

What date column should I use? A datetime column that stays fixed for old rows, such as order date or invoice date. Avoid a "last modified" column for the partition filter itself, because rows would jump between partitions.

Why did my refresh not get faster after I turned it on? Almost always query folding. If the RangeStart and RangeEnd filter doesn't fold into a WHERE clause at the source, Power BI pulls the whole table and filters in memory. Check "View Native Query" on the step after your date filter.

Can I change the policy after publishing? Yes. Edit the incremental refresh settings in Power BI Desktop and republish. If you changed the ranges, the next refresh rebuilds the affected partitions.

How many days should I refresh incrementally? Start with the window where late-arriving or corrected data lands, often 3 to 10 days. If corrections can hit records a month back, widen the window to cover that.

Does it reduce load on our source database? Yes. After the first run, each refresh reads only the recent partitions, so the nightly hit on the source drops from all rows to a few days of rows.
