[0:45-2:15] VALUE BEAT 1 - What's eating my memory on refresh? (MODALITY: custom animation) (ON-SCREEN CLAIM CARD: "A flat table blows up because every column repeats.") Spoken: "Here's what happens on refresh. Power BI has to load the model into memory, and during a refresh it keeps the old copy while it builds the new one, so for a moment it needs close to twice the size of your data in RAM. If your whole report is one wide flat table, with the customer name, region, product, and category repeated on every single row, that table is huge, and doubling it is what tips you over into an out-of-memory refresh. The storage engine compresses columns, and it compresses far better when a column has a few repeated values than when it's long unique text stretched across millions of rows." [2:15-4:00] VALUE BEAT 2 - What is a star schema, and why is it faster? (MODALITY: screen-record - Power BI Desktop, Model view) (ON-SCREEN CLAIM CARD: "A star schema is one fact table surrounded by dimension tables.") Spoken: "Open the model view in Power BI Desktop and this is the shape you want. In the middle, one fact table. That's your events, the things that happen over and over, like sales order lines, each row a transaction with its numbers and a few ID columns. Around it, separate dimension tables for the things you filter and group by. A customer table, a product table, a date table, a region table. Each dimension lists every item once, with a short ID, and the fact table just points at that ID instead of repeating the full text. Sales drops from a hundred columns of repeated text to a narrow table of numbers and IDs, and the descriptions live once in the dimensions. That's why it compresses smaller and scans faster." (SCREEN-RECORD spec: drag Sales into the center; drag Customer, Product, Date, Region out to the corners; cursor moves to the Sales table as it shrinks from 100 columns to 8 as text columns are removed; lower-third label "FACT" on Sales, "DIMENSION" on each outer table.) (ON-SCREEN TAKEAWAY CARD: "2 - One fact table for events, separate dimensions for what you slice by.") Spoken (payoff): "Takeaway two. One fact table for the events you measure, separate dimension tables for the things you slice by. That is a star schema." Re-hook: "Now, if one fact table with a set of dimensions is the target, where does snowflake come in, and is it ever worth it."

[4:00-5:45] VALUE BEAT 3 - Star schema vs snowflake: which do I build? (MODALITY: custom animation) (ON-SCREEN CLAIM CARD: "Snowflake splits one dimension into several joined tables.") Spoken: "A snowflake schema takes a dimension and normalizes it further. Instead of one product table, you get product, then a separate product subcategory table, then a category table, each linked to the next. It saves a tiny bit of space and it matches how a source database is often built. The cost shows up at query time. Every filter now travels through more joins to reach the fact table, and in Power BI those extra relationships usually make the model harder to read and a little slower, for savings you won't notice. For most Power BI reports, combine those chains back into one flat dimension. Keep product, subcategory, and category as columns in a single product table. Stop at star. The one time snowflake earns its place is when a sub-table is very large and shared by several facts, or when a dimension has millions of rows you don't want duplicated. Short of that, star wins." (CUSTOM ANIMATION spec: a single Product dimension splits apart into Product → Subcategory → Category, three tables chained by join arrows; a small filter dot has to hop through all three arrows to reach the fact table, visibly slower; then the three tables fold back into one Product box and the dot reaches the fact table in a single hop. Brand color #1D967C; the extra join arrows flash amber as friction, not as an accent.) (ON-SCREEN TAKEAWAY CARD: "3 - Stop at star. Only snowflake a very large, shared dimension.") Spoken (payoff): "Takeaway three. Stop at a star schema. Only snowflake a dimension when the sub-table is very large and reused across several fact tables." Re-hook: "Fine, the target's clear. Next is the part people skip. Turning the flat table you already have into that shape."

[5:45-7:45] VALUE BEAT 4 - How do I turn my flat table into a star schema? (MODALITY: screen-record - Power Query editor) (ON-SCREEN CLAIM CARD: "Build dimensions from your flat table with reference queries.") Spoken: "Here's the build in Power Query. Start from your one flat table. Right-click it and choose reference, so you get a query that points at the same source. Rename it Customer. Keep only the customer columns, then remove duplicate rows so you're left with one row per customer. Do the same for product and region. Each reference becomes a clean dimension. Now give every dimension a short ID column if it doesn't have one. The fact table keeps the numbers and the ID columns, and you remove the long text columns from it, because those now live in the dimensions. Load it all, and in model view you'll see the fact table in the middle with dimensions around it. That's the star, built from data you already had." (SCREEN-RECORD spec: right-click the flat query, click Reference; rename to Customer; remove columns down to customer fields; Home → Remove Rows → Remove Duplicates; repeat quick-cut for Product and Region; back on the fact query, multi-select and delete the text columns; Close & Apply; cut to Model view resolving into a star. Callout box each time a dimension row count drops from millions to a few thousand.) (ON-SCREEN TAKEAWAY CARD: "4 - Reference query → remove duplicates → strip text out of the fact table.") Spoken (payoff): "Takeaway four. Build each dimension as a reference query, remove duplicates down to one row per item, and strip the repeated text columns out of the fact table." Re-hook: "The tables are there. They do nothing until you connect them properly, and this is where a lot of models leak or slow down."

[7:45-9:30] VALUE BEAT 5 - Which relationships and keys do I set up? (MODALITY: custom animation) (ON-SCREEN CLAIM CARD: "Connect each dimension one-to-many, single direction.") Spoken: "In model view, drag the ID from each dimension onto the matching ID in the fact table. You want a one-to-many relationship, the one side on the dimension, the many side on the fact table, and the filter direction set to single, so the dimension filters the fact and not the other way around. Leave bi-directional off unless you have a specific reason, because it's slower and it can produce ambiguous results. Match on an integer ID where you can, because integers compress and scan faster than text. Once every dimension is joined like this, a filter on the customer table flows straight down into sales, and every measure you write reads cleaner and runs faster. This shape is also what Copilot and any AI feature needs to return one correct number, because it can follow the relationships instead of guessing." (CUSTOM ANIMATION spec: an ID column lifts out of the Customer table and drops onto CustomerID in the fact table; a "1" badge lights on the dimension end, a "many" badge on the fact end; the filter arrow points one way only (dimension → fact). A user clicks a customer and the filter cascades down into the fact rows. A ghosted bi-directional arrow appears, turns amber, and is switched off. Brand color #1D967C throughout.) (ON-SCREEN TAKEAWAY CARD: "5 - One-to-many, single-direction filter, on an integer ID.") Spoken (payoff): "Takeaway five. Join each dimension to the fact table one-to-many, single-direction filter, on an integer ID." Re-hook: "Model's built. Does it move any faster than before. Time to measure it, and to pay off that checkbox I promised."

[9:30-11:15] How do I check the model is really faster? (MODALITY: screen-record + data-viz) (ON-SCREEN CLAIM CARD: "Measure it with Performance Analyzer and the model size.") Spoken: "Don't take my word for it, measure. In Power BI Desktop open the optimize ribbon and turn on Performance Analyzer, then refresh the visuals and read the timings before and after your rebuild. Check the model size too. Save the file and look at how much smaller the star version is on disk, or use a free tool like DAX Studio to read the VertiPaq stats and see which columns eat the most memory. On a real rebuild you'll usually watch a refresh that ran for many minutes finish in a fraction of the time, on the same data, because the model got smaller and the joins got simpler. And here's the checkbox I promised. Go to options, data load, and turn off Auto date/time. Left on, Power BI creates a hidden date table behind every single date column in your model, and each one inflates the file. Turn it off, then build one proper date table and connect it to the fact table like any other dimension. On models with a lot of date fields, that one setting alone can cut the size by a noticeable chunk."
