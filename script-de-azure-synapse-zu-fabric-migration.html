[0:45-2:20] VALUE BEAT 1 - Was passiert mit meinen Dedicated SQL Pools? (MODALITY: screen-record - Synapse Studio, dann Fabric Warehouse)

CLAIM (ON-SCREEN Text-Karte): "Ihr Dedicated SQL Pool zieht nicht um. Er wird neu gebaut." Fangen wir mit dem Kern an, den fast alle zuerst im Kopf haben: dem Dedicated SQL Pool. Microsoft führt die dedizierten SQL-Pools von Synapse aus, das Gegenstück in Fabric heißt Warehouse. Und ja, das meiste an T-SQL, das Sie kennen, funktioniert dort weiter. Die böse Überraschung steckt woanders.

PROOF / DEMO (screen-record): Schauen Sie mit mir auf den Bildschirm. Links Synapse Studio, rechts ein leeres Fabric Warehouse. Es gibt keinen In-Place-Upgrade-Pfad zwischen den beiden. Was Sie machen: Sie skripten Ihr Schema aus dem SQL Pool heraus, also Tabellen, Views, gespeicherte Prozeduren. Hier, "Generate Scripts", alles markieren, exportieren. Das Konzept mit Distribution und Hash-Verteilung, das Sie aus dem dedizierten Pool kennen, brauchen Sie in Fabric so nicht mehr, das übernimmt die Plattform anders. Sie legen die Struktur im Warehouse neu an und laden die Daten frisch. (Cursor-Spotlight auf "Generate Scripts"; Callout-Box "kein In-Place-Upgrade"; Split-Screen Synapse links, Fabric rechts.)

PAYOFF (ON-SCREEN nummerierte Karte "Takeaway 1"): Das ist Ihr erster konkreter Schritt für heute Nachmittag. Skripten Sie Ihr Schema aus dem SQL Pool heraus, bevor Sie sonst irgendetwas anfassen. Dieses Skript ist Ihre Landkarte für den ganzen Umzug.

RE-HOOK: Das Schema ist der einfache Teil. Bei den Pipelines wird's ungemütlich.

[2:20-4:00] VALUE BEAT 2 - Wohin gehen meine Synapse-Pipelines? (MODALITY: custom animation - Pipeline-Neubau)

CLAIM (ON-SCREEN Text-Karte): "Synapse-Pipelines lassen sich nicht importieren." Jetzt der Teil, der wehtut. Ihre Synapse-Pipelines. Technisch sind die nah an Azure Data Factory, und trotzdem können Sie einen Synapse-Workspace nicht einfach nach Fabric importieren.

PROOF / DEMO (CUSTOM ANIMATION): Zeigen Sie das so animiert: Links ein Block mit fünf Synapse-Pipeline-Kacheln, jede mit Quelle, Aktivität, Ziel. In der Mitte eine Barriere mit dem Label "kein Workspace-Import". Rechts das Fabric-Data-Factory-Feld, leer. Dann wandert jede Kachel einzeln von links nach rechts und wird beim Übergang neu aufgebaut: Linked Services werden zu Fabric-Connections, die Integration Runtime fällt weg, die Aktivitäten setzen Sie neu zusammen. Die alte JSON-Definition dient nur als Vorlage zum Abschreiben, nicht als Datei zum Hochladen. Jede Kachel, die rüberwandert, zählt am Rand einen Zähler hoch: "1 von 5 neu gebaut". (Ein-und-derselbe Zähler tickt sichtbar, das hält das Auge alle paar Sekunden am Fortschritt.)

PAYOFF (ON-SCREEN nummerierte Karte "Takeaway 2"): Bevor Sie eine einzige Pipeline nachbauen: Inventarisieren Sie alle in einer Tabelle. Quelle, Ziel, Zeitplan, letzter erfolgreicher Lauf. Diese Liste ist Ihr Bauplan, und sie zeigt Ihnen ganz nebenbei, welche Pipeline seit Monaten niemand mehr braucht. Die bauen Sie dann gar nicht erst nach.

RE-HOOK: Gut. Jetzt die Frage, bei der die meisten Angst vor doppeltem Speicher bekommen: die Daten selbst.

[4:00-5:45] VALUE BEAT 3 - Wie kommen die Daten rüber, ohne alles doppelt zu kopieren? (MODALITY: screen-record + data-viz)

CLAIM (ON-SCREEN Text-Karte): "Ihre Daten müssen Sie oft gar nicht kopieren." Viele planen für den Umzug erst mal Tage für das Kopieren von Terabytes ein. Bei einem großen Teil Ihrer Daten sparen Sie sich das komplett.

PROOF / DEMO (screen-record + eingeblendete data-viz): Hier auf dem Bildschirm lege ich in OneLake einen Shortcut an. OneLake ist die Speicherschicht unter Fabric. Der Shortcut zeigt direkt auf Ihren bestehenden Azure Data Lake Storage, dort, wo Ihre Synapse-Daten schon liegen. Fabric liest sie an Ort und Stelle, ohne eine zweite Kopie. Daneben blende ich das kurz als Grafik ein: eine physische Kopie in der Mitte, drei Fabric-Arbeitsbereiche, die alle mit einem Pfeil darauf zeigen. Ein Speicher, mehrere Zugriffe, keine Vervielfältigung. Für das Warehouse laden Sie am Ende strukturiert, aber für Ihre Lake-Daten ist der Shortcut der schnellere und billigere Weg. (Data-viz: ein Zylinder "1x Speicher" zentral, drei Workspace-Boxen mit aufleuchtenden Verbindungspfeilen.)

PAYOFF (ON-SCREEN nummerierte Karte "Takeaway 3"): Bevor Sie irgendetwas kopieren, prüfen Sie pro Datenquelle: Geht das per Shortcut? Jede vermiedene Kopie spart Ihnen Speicherkosten und später Refresh-Zeit.

RE-HOOK: Jetzt haben Sie alle Einzelteile. Ob's am Ende teuer wird, entscheidet die Reihenfolge.

[5:45-7:40] VALUE BEAT 4 - In welcher Reihenfolge baue ich das Ganze um? (MODALITY: custom animation - Medaillon-Schichten)

CLAIM (ON-SCREEN Text-Karte): "Bauen Sie von der Datenschicht nach oben." Der häufigste Reihenfolge-Fehler: Man fängt beim Dashboard an, weil das jeder sehen will. Und dann steht der schöne Report auf einem Fundament, das es noch gar nicht gibt.

PROOF / DEMO (CUSTOM ANIMATION - Bronze, Silber, Gold): Animieren Sie drei Schichten übereinander. Unten Bronze: die Rohdaten landen per Shortcut, unverändert. Sie sehen Datentropfen von links einfließen. Darüber Silber: die Transformationen, die Sie aus den Pipelines nachgebaut haben, reinigen und verbinden die Daten, die Farbe wird klarer. Ganz oben Gold: das fertige Warehouse-Modell mit Ihren Kennzahlen und Ihren Zugriffsregeln. Erst wenn Gold steht, dockt der Power-BI-Report an, animiert als letzte Kachel, die sich oben andockt. Die Reihenfolge im Bild ist die Reihenfolge im Projekt: unten anfangen, nach oben arbeiten, Report zuletzt. (Jede Schicht leuchtet nacheinander auf; der Report klinkt sich sichtbar als letztes ein.)

PAYOFF (ON-SCREEN nummerierte Karte "Takeaway 4"): Migrieren Sie Datenstrom für Datenstrom, nicht alles auf einmal. Ein einziger sauber umgezogener Datenfluss, der in Produktion läuft, ist mehr wert als zehn halbfertige. Bringen Sie einen komplett durch, von Bronze bis zum Report, dann den nächsten.

RE-HOOK: Und jetzt kommt genau der Punkt, der die Rechnung sprengt, der aus dem Anfang.

[7:40-9:30] VALUE BEAT 5 - Warum wird Fabric plötzlich teurer als gedacht? (MODALITY: data-viz - CU-Auslastung und Drosselung)

CLAIM (ON-SCREEN Text-Karte): "Zwei Umgebungen parallel plus 1:1-Kopie treiben die Rechnung." Hier lösen wir die Frage vom Anfang auf. Fabric rechnet über Capacity ab, gemessen in Capacity Units. Zwei Dinge treiben diese Rechnung hoch, und beide sind vermeidbar.

PROOF / DEMO (data-viz - animierter CU-Verlauf): Sehen Sie sich diese Kurve an. Erstens: Sie lassen Synapse und Fabric monatelang parallel laufen, weil niemand sich traut, das Alte abzuschalten. Zwei Rechnungen gleichzeitig. Zweitens: Sie heben Ihren Dedicated SQL Pool 1:1 nach Fabric, ohne neu zu modellieren. Dann liegt die alte, schwere Last auf der neuen Capacity. Im Diagramm füllt sich der CU-Balken, das Smoothing verteilt die Spitzen und sieht erst mal harmlos aus, dann überschreitet die Auslastung die Linie und Fabric drosselt. Ihre Berichte werden langsam, und auf dem Dashboard sieht die Auslastung trotzdem in Ordnung aus. Das ist die Falle. (CU-Balken füllt sich; Smoothing-Kurve glättet; rote Drossel-Linie wird überschritten; Anfragen stauen sich sichtbar.)

PAYOFF (ON-SCREEN nummerierte Karte "Takeaway 5"): Setzen Sie ein hartes Enddatum für die Parallelphase, schriftlich, mit einem Verantwortlichen. Und modellieren Sie beim Umzug neu, statt 1:1 zu heben. Das ist der Unterschied zwischen einer passend gewählten F-Kapazität und der doppelten Rechnung.

RE-HOOK: Damit das nicht abstrakt bleibt, gehen wir einen echten Ablauf durch.

[9:30-12:00] WORKED EXAMPLE - Wie sieht ein echter Umzug in acht Wochen aus? (MODALITY: screen-record + b-roll) (ON-SCREEN: Zeitstrahl "Woche 1 bis Woche 8")

Ein Wort zur Einordnung vorab. Microsoft hat auf der Ignite 2025 über 28.000 Kundenorganisationen für Fabric gemeldet, das am schnellsten wachsende Analytics-Produkt in der Geschichte des Unternehmens. Der Weg ist also gut ausgetreten. Nur bleibt der Umzug eben Handarbeit. So sieht ein realistischer Plan für ein mittelgroßes Setup aus, acht Wochen, Woche für Woche.

(B-roll: ein Team am Whiteboard, dann Cut auf den Zeitstrahl, jede Woche leuchtet beim Nennen auf.)

Woche 1: Bestandsaufnahme. Sie skripten das Schema und inventarisieren jede Pipeline in Ihrer Tabelle. Sie streichen schon hier alles, was niemand mehr braucht. Woche 2: Sie stellen die Fabric-Capacity bereit, richten das Warehouse ein und legen die Schema-Struktur aus Ihrem Skript neu an. Woche 3 und 4: Sie binden die Rohdaten per OneLake-Shortcut an und bauen die drei bis fünf wichtigsten Pipelines in Fabric Data Factory nach. Woche 5: Sie setzen die Transformationen für die Silber-Schicht neu auf und prüfen die Ergebnisse gegen die alten Synapse-Ausgaben, Zeile für Zeile. Woche 6: Sie bauen das Warehouse-Modell zu Ende, definieren die Kennzahlen und setzen Ihre Zugriffsregeln mit Row-Level Security. Woche 7: Sie hängen die Power-BI-Berichte um, lassen alt und neu kurz parallel laufen und validieren, dass dieselbe Frage in beiden Umgebungen dieselbe Zahl liefert. Woche 8: Cut-over. Sie schalten produktiv auf Fabric, und Sie schalten Synapse ab. Genau dieses Abschalten ist der Schritt, den ich am Anfang meinte. Wer die Parallelphase offen lässt, zahlt Monat für Monat doppelt.

(Screen-record: kurzer Blick auf die Fabric Capacity Metrics App, wie die Auslastung nach dem Abschalten von Synapse sichtbar sinkt.)

[12:00-13:15] PAYOFF - Recap + offene Schleife auflösen (MODALITY: on-screen text / kinetic type - die fünf Takeaways als Liste) (ON-SCREEN: nacheinander einfliegend)

Fassen wir zusammen, damit Sie den kompletten Umzug in der Hand haben: Eins: Skripten Sie Ihr Schema aus dem SQL Pool. Das ist Ihre Landkarte. Zwei: Inventarisieren Sie jede Pipeline und bauen Sie sie einzeln neu. Die alte JSON ist nur Vorlage. Drei: Binden Sie Daten per OneLake-Shortcut an, statt zu kopieren, wo es geht. Vier: Bauen Sie von unten nach oben, Datenstrom für Datenstrom, Report zuletzt. Fünf: Hartes Enddatum für die Parallelphase, und neu modellieren statt 1:1 heben.

Und die offene Frage vom Anfang, der eine Schritt, der Projekte doppelt so teuer macht: Es ist genau diese Parallelphase in Woche acht. Nicht das Kopieren, nicht die Pipelines. Sondern dass niemand den Stecker beim Alten zieht. Setzen Sie das Enddatum, bevor Sie überhaupt anfangen.

Kurz zusammengefasst: Es gibt keinen automatischen Weg von Azure Synapse zu Microsoft Fabric. Der Dedicated SQL Pool wird als Fabric Warehouse neu gebaut, Synapse-Pipelines werden in Fabric Data Factory von Hand nachgebaut, und Ihre Daten binden Sie oft per OneLake-Shortcut an, statt sie zu kopieren. Wer von der Datenschicht nach oben migriert und die Parallelphase kurz hält, hält auch die Fabric-Capacity-Kosten im Griff. Diese Anleitung zeigt die Reihenfolge und einen realistischen Acht-Wochen-Plan.
