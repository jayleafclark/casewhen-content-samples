[0:40-2:20] VALUE BEAT 1 - Which Azure SQL do I pick?

CLAIM: "There are three Azure SQL targets, and your SSIS and SQL Agent jobs usually pick for you."

(MODALITY: animation) (ON-SCREEN CLAIM CARD: "3 targets. Your T-SQL surface decides.")

PROOF/DEMO (custom animation of the three-target fork): One box on the left labelled "On-prem SQL Server + SSIS" splits into three doors. Door 1 "Azure SQL Database" lights up cheapest, then three red tags drop off it reading "no SQL Agent", "no cross-database queries", "reduced T-SQL". Door 2 "Azure SQL Managed Instance" lights up and keeps green checks reading "SQL Agent", "cross-database queries", "CLR", "near-full T-SQL surface". Door 3 "SQL Server on Azure VM" keeps every green check plus a wrench icon labelled "you patch and back up". The legacy box slides through Door 2 as Austin lands the rule.

Spoken: "Azure gives you three doors. Azure SQL Database is one managed database, cheapest at the low end, and it drops SQL Agent, cross-database queries, and a chunk of T-SQL. Azure SQL Managed Instance keeps almost the whole SQL Server surface, Agent jobs, cross-database queries, CLR, so a legacy estate lands there with the least rewriting. SQL Server on an Azure VM keeps every feature and hands you the patching and backups to run yourself. If you've got Agent jobs and packages talking across databases, single database sends you into a rewrite you never budgeted. Managed Instance costs more at the floor and saves you weeks of code changes."

PAYOFF (numbered takeaway): "Takeaway one: match the target to your T-SQL surface first, price second. Agent jobs and cross-database queries mean Managed Instance."

(ON-SCREEN TAKEAWAY: "1 - Target = your T-SQL surface. Agent + cross-db => Managed Instance.")

RE-HOOK: "Target picked. Now the packages, because SSIS is where the runtime bill hides."

[2:20-4:00] VALUE BEAT 2 - What happens to my SSIS packages?

CLAIM: "Your SSIS packages lift to Azure, but the runtime that hosts them bills by the hour whether it's working or sitting idle."

(MODALITY: screen-record) (ON-SCREEN CLAIM CARD: "SSIS moves. The runtime bills 24/7 unless you stop it.")

PROOF/DEMO (screen-record Azure Data Factory, then a custom animation of the idle meter): Screen-record shows the Azure Data Factory portal, the Azure-SSIS Integration Runtime pane, and a package deployed to the SSISDB catalog on Managed Instance. Then cut to a custom animation: a small cluster of three VM tiles labelled "Azure-SSIS IR". A clock spins across a 24-hour bar. A dollar meter ticks up every hour the tiles glow, but the tiles only do work for a 40-minute slice near 2am. The rest of the bar shows glowing tiles doing nothing while the meter keeps climbing. Then a "start / stop trigger" chip snaps onto the timeline, the tiles go dark outside the 40-minute slice, and the meter flattens.

Spoken: "SSIS moves in two parts. The catalog, SSISDB, goes onto your Azure SQL Managed Instance. The packages run on an Azure-SSIS Integration Runtime inside Azure Data Factory, which is a cluster of virtual machines Azure spins up for you. That cluster bills per node, per hour, every hour it's switched on. A lot of teams provision it, point their nightly load at it, and leave it running. If your load runs forty minutes and the cluster sits on all day, you're paying for roughly twenty-three hours of an idle cluster. Put a start-and-stop schedule on it with a trigger in Data Factory, and that line drops to the minutes you use."

PAYOFF (numbered takeaway): "Takeaway two: schedule the Azure-SSIS runtime to start before the load and stop after, on day one. Idle compute is the number one surprise on the first invoice."

(ON-SCREEN TAKEAWAY: "2 - Start/stop the Azure-SSIS IR. Never pay for idle.")

RE-HOOK: "Runtime handled. Next, how big to make the database, because over-sizing is the other easy leak."

(MODALITY on re-hook: talking head, cut to b-roll of a server rack for two seconds under the line.)

PROOF/DEMO (custom animation of vCore throttling, then a data-viz): Animation shows two meters side by side, "CPU" and "Log IO", with a ceiling line marked "your vCore tier". A workload wave rises. Then cut to a data-viz: a usage histogram of real load over a week, with a marker on the 95th percentile far below the rare peak. Spoken: "Azure SQL sells you a ceiling, measured in vCores or DTUs. Cross it and Azure governs you, your queries queue, log writes throttle, latency climbs. Nobody wants that call, so teams buy the biggest tier and sleep better while paying for cores that sit idle. The move is to measure first. The Azure SQL Migration extension in Azure Data Studio reads your live workload and recommends a size from real numbers. Size to your 95th percentile load with a little room, then scale up later in seconds if you need it. Scaling Azure SQL up is a slider, so you don't have to guess high."

PAYOFF (numbered takeaway): "Takeaway three: size from measured load at the 95th percentile, then scale on demand. You can always go up in seconds, so stop paying for peak-of-peak all year."

A second chip labelled "1-year / 3-year reservation" clicks in, and the cost bar drops a second step. A caption reads "per Microsoft pricing: up to 55% vs pay-as-you-go".

Spoken: "This is the part that pays for the project. If you already own SQL Server licenses with Software Assurance, Azure Hybrid Benefit lets you carry them onto Azure SQL and drop the compute rate. On Managed Instance it can even cover a block of vCores at no extra license cost. Stack that with reserved capacity, where you commit to one or three years up front, and Microsoft's own figure is up to fifty-five percent off pay-as-you-go. Both are off by default. Nobody at the portal turns them on for you. It's a checkbox and a reservation, no code, no downtime."

PAYOFF (numbered takeaway): "Takeaway four: switch on Azure Hybrid Benefit and buy reserved capacity once the size settles. That's up to fifty-five percent off the same database, on Microsoft's own pricing."

[7:30-10:15] VALUE BEAT 5 - Can I move it without a weekend outage?

CLAIM: "Keep the old server live and cut over in minutes with an online migration, instead of taking a downtime window."

(MODALITY: animation) (ON-SCREEN CLAIM CARD: "Offline = outage window. Online = cut over in minutes.")

PROOF/DEMO (custom animation of online log replay, then a short screen-record of Database Migration Service): Animation shows the on-prem SQL Server on the left still serving little user icons. Azure Database Migration Service does an initial bulk load (a big block slides to the Azure target on the right), then a thin stream of "transaction log" records keeps flowing left to right, keeping both databases matched. At cutover, the little user icons wait for a beat, a switch labelled "connection string" flips from on-prem to Azure, and the users resume on the Azure side. A timer shows "downtime: ~10 min". Then a two-second screen-record of the DMS migration project status page showing "continuous sync".

Spoken: "There are two ways to cut over. Offline is the simple one. You stop the source, back up, restore into Azure SQL, repoint, done. It works, but it needs a downtime window, which for a warehouse can be a whole weekend. Online keeps the old server serving users. Azure Database Migration Service loads the data once, then keeps replaying the transaction log from your on-prem server to Azure so the two stay matched. When you're ready, you pick a quiet ten minutes, stop writes, let the last log records drain, and repoint the connection strings. Downtime goes from a weekend to minutes. Online costs a bit more to set up and needs the source reachable from Azure, so weigh it against how much an outage costs the business."

PAYOFF (numbered takeaway): "Takeaway five: if downtime is expensive, run an online migration with Database Migration Service and cut over on log replay. Minutes, not a weekend."

(ON-SCREEN TAKEAWAY: "5 - Expensive downtime? Online migration + log replay. Cut over in minutes.")

RE-HOOK: "It's live on Azure. So why are some reports suddenly slower? That trips almost everyone."

(MODALITY on re-hook: talking head, quick b-roll cutaway of a loading spinner for one second.)

[10:15-12:15] VALUE BEAT 6 - Why are my reports slower now?

CLAIM: "After a clean move, some queries run slower, and it's almost always the compatibility level and a cold plan cache."

(MODALITY: screen-record) (ON-SCREEN CLAIM CARD: "Slower after cutover? Compatibility level + cold cache.")

PROOF/DEMO (screen-record Query Store, then a custom animation of the plan swap): Screen-record shows the database Compatibility level dropdown in the Azure SQL settings, set from 160 down to 140 to match the old server. Then the Query Store "Regressed Queries" view opens, showing one query with two plans, an old fast plan and a new slow one, and the "Force Plan" button. Cut to a custom animation: one SQL query flows into an optimizer box; at compatibility level 160 it exits on a long winding path (slow), at level 140 it exits on a short straight path (fast). A "Force Plan" stamp locks the short path in.

Spoken: "A migration can go perfectly and still hand you a slower report on Monday. Two reasons. First, Azure SQL sets the database to the newest compatibility level, which changes how the optimizer builds query plans. Your old server ran an older level, some plans were tuned around it, and the new optimizer picks a different plan that happens to be worse for that one query. Second, the plan cache starts empty after cutover, so the first runs compile cold and feel slow before they settle. The fix is order. Set the compatibility level to match your old server before you move, get it stable, then raise it one step at a time with Query Store turned on. Query Store keeps the history of every plan, shows you the one that regressed, and lets you force the fast plan back with a click. A regression becomes a five-minute fix instead of a mystery."

PAYOFF (numbered takeaway): "Takeaway six: migrate on your old compatibility level, turn on Query Store, and raise the level in steps. When a plan regresses, force the good one and move on."

(ON-SCREEN TAKEAWAY: "6 - Keep old compat level, enable Query Store, raise in steps. Force good plans.")

RE-HOOK: "That's the whole move. So let's add up what it really costs."

(MODALITY on re-hook: talking head into kinetic type.)
