Migrate SQL to Azure SQL: what breaks, and how to catch it before go-live

Quick answer. To migrate SQL to Azure SQL, first pick the right target: Azure SQL Database for a self-contained app, or Managed Instance when you need SQL Server Agent, cross-database queries, or linked servers. Run Data Migration Assistant to find blockers, move the data with Azure Database Migration Service, then compare row counts before you cut over. ---

If you plan to migrate SQL to Azure SQL, moving the data is the easy part. The hard part is catching what changed during the move. A stored procedure times out at month-end. A nightly load never runs. A report shows half the rows it did last week. None of that shows up while you are copying tables. It shows up three weeks after go-live, in front of the people who trust the numbers.

Here is the checklist we run on real projects, in order.

Why do SQL to Azure SQL migrations break after go-live?

Azure SQL runs a trimmed set of the features you get on a SQL Server you host yourself. That is the whole problem in one line.

Azure SQL Database, the platform-as-a-service option, drops several server-level features. There is no SQL Server Agent. Cross-database queries do not work by default. Linked servers are gone. Database Mail is gone. Azure SQL Managed Instance keeps most of them, which is why the choice of target matters so much.

Most teams test the tables and forget the jobs and connections. The data lands fine, so the move looks done. Then the first month-end close finds the gap: the scheduled load that used to run at 2 a.m. was never recreated, and no report warns you. The report just goes stale.

Which Azure SQL target should you pick?

You have three targets. The choice decides how much you rebuild after the move.

TargetBest forKeeps SQL Agent, cross-db, linked servers?Change needed
Azure SQL DatabaseOne app database, cloud-native scalingNoHigher if the app uses server-level features
Azure SQL Managed InstanceLifting a SQL Server with jobs and dependenciesYesLower, near full compatibility
SQL Server on Azure VMFull control and OS accessYes, full SQL ServerLowest code change, highest upkeep

Most business databases land on one of the first two. Pick Azure SQL Database when the app is self-contained and you want the cloud to handle scaling and patching. It also offers a Hyperscale tier for very large databases. Pick Managed Instance when you rely on SQL Agent jobs, three-part names, or linked servers, since it gives you close to full SQL Server compatibility.

The VM option is a straight lift. You keep the whole SQL Server, and you also keep every task that comes with running your own server: patching, backups, and OS updates. Most teams use it only when a feature will not run anywhere else.

Decide this before you migrate to Azure SQL, because changing the target later means redoing the move.

How do you migrate SQL to Azure SQL step by step?

  1. Assess first. Run Data Migration Assistant, a free Microsoft tool. It reads your database and lists blockers and behavior changes before you touch anything. Read the whole report, not the summary line.
  2. Pick the target from that report. Database, Managed Instance, or VM. Let the blockers decide, not a preference.
  3. Right-size the tier. Azure SQL uses vCore or DTU pricing. Start from your current CPU, memory, and storage numbers, not a guess. You can scale up later, so start close and adjust.
  4. Move the data. For small databases, export a BACPAC with `sqlpackage`. For large databases or near-zero downtime, use Azure Database Migration Service in online mode, which keeps the source running while it syncs.
  5. Rebuild what does not travel. SQL Agent jobs move to Elastic Jobs or the Managed Instance Agent. Recreate linked servers and Database Mail where you still need them.
  6. Repoint connection strings. Add retry logic for transient faults, because Azure SQL will drop a connection now and then.
  7. Validate, then cut over in a low-traffic window.

Steps 1 and 4 get all the attention. Step 5 is where most surprises come from, because it covers everything that lives outside the tables. Give it a full day of its own and write down each job you rebuild.

What breaks that nobody warns you about?

Five things trip up almost every first migration.

SQL Server Agent jobs. Azure SQL Database has no Agent at all. Your nightly load just stops running. Use Elastic Jobs, or move to Managed Instance, which has its own Agent.

Cross-database queries. Three-part names like `sales.dbo.orders` return an error on Azure SQL Database. Managed Instance supports them, so if your code joins across databases, that alone can decide the target.

Linked servers. Same story. They work on Managed Instance and on a VM, and they are gone on Azure SQL Database. Replacing them often means rewriting a report or an integration.

Connection drops. Azure SQL moves your database to a new node during maintenance and failovers. A connection that always worked will now drop sometimes. Apps without retry logic throw errors that look random and waste a day of debugging.

Collation and compatibility level. Set the compatibility level to match the old server first. Test on that. Then raise it on purpose once you have proof the queries still behave.

How do you know the migration really worked?

Do not trust a green checkmark. Trust counts.

Compare row counts table by table, old against new. Run a checksum on the big tables. Replay a real workload and watch Query Store for queries that got slower after the move. Look hard at your ten slowest reports, because those are the ones users notice.

This step earns its time. A migration that drops rows or slows queries corrupts every report built on that data. Poor data quality costs organizations $12.9M per year on average (Gartner). A small row-count gap after a move is exactly how a bill like that starts, and it hides for weeks because the numbers still look plausible.

Keep the old database in read-only mode for a rollback window, say two weeks, before you retire it. If your dashboards read from this database, treat your reporting move as a separate track. A Tableau to Power BI migration, for example, should wait until the data layer is stable. Move the data first, prove it, then move the reports on top of it.

Frequently asked questions

How long does it take to migrate SQL to Azure SQL? Assessment takes a day or two. The data move can take a few hours. Validation and rebuilding jobs take the most time, often one to two weeks for a database with real dependencies. A clean, self-contained database can go faster.

Do I need Managed Instance or Azure SQL Database? If you run Agent jobs, join across databases, or depend on linked servers, choose Managed Instance. If the database stands on its own, Azure SQL Database costs less and scales more easily. When you are unsure, let the Data Migration Assistant report make the call for you.

Will my apps need code changes? Connection strings change, and you should add retry logic for transient faults. On Azure SQL Database, three-part names and linked servers need rework. Managed Instance usually needs the least code change.

Can I migrate with almost no downtime? Yes. Azure Database Migration Service has an online mode. It keeps the source running while it syncs, so cutover is a short switch instead of a long outage.

What happens to my backups? Azure SQL takes automatic backups and supports point-in-time restore, up to 35 days by default. You do not manage the backup schedule yourself, which removes one job you used to own.

Is Data Migration Assistant free? Yes. It is a free Microsoft download, and running it before you plan anything is the cheapest hour in the whole project.
