Power BI Row Level Security Is Only As Good As Your Test

Quick answer: Power BI row level security (RLS) controls which rows each person sees inside one report, based on their role. You write a role with a DAX filter in Power BI Desktop, publish the model, assign people in the service, and test with View As. Done right, two managers open the same report and each sees only their own numbers. ---

Most teams set up Power BI row level security once, test it with their own admin login, and never learn that a regional manager can open the report and read the whole company's numbers. The demo looked right. Six weeks later a manager spots another region's margin in a report everyone shares, and confidence in every dashboard drops in a single afternoon.

That's the pattern we get called in to clean up. The setup was fine on the screen where it was built. It was never checked from the seat of the person it was meant to restrict. Below is what row level security does, why it goes wrong in the exact moment it matters, and the steps you can run today to prove it works.

What is Power BI row level security, in plain terms?

Power BI row level security filters the rows inside a single dataset (the semantic model) based on who is signed in. Everyone opens the same report. The visuals stay identical. The data behind them changes per person.

You build it in Power BI Desktop under the Modeling tab, in the Manage roles dialog. A role is a name plus a DAX filter on one or more tables. A simple one looks like this on a Sales table:

``` [Region] = "West" ```

Anyone in that role sees only West rows. Every measure, every total, every drill-down respects the filter automatically. You don't touch the visuals at all. That's the part people miss: a report can look complete and still be wide open, because no role is a role too, and the default is that a viewer sees everything.

Why does row level security break trust in a board meeting?

Picture month-end. The finance lead shares one revenue report with 40 managers instead of emailing 40 spreadsheets. If a single role has the wrong DAX filter, one manager sees a peer's margin, or opens a blank page and assumes the report is down. Either way, that person goes back to their own file, and so does everyone they tell.

The stakes here are real. In the 2025 Data Integrity Trends study from Drexel LeBow and Precisely, 67% of organizations said they don't fully trust the data they use to make decisions. One wrong-row incident is exactly how a report joins that pile. The mechanism is usually one of three things: no role assigned so the viewer sees all rows, a filter that matches nothing so the page looks empty, or a bidirectional relationship that carries extra rows around the filter you set. That last one catches good teams, so set relationships to single-direction filtering wherever RLS is involved and test the edges.

How do you set up roles and test them with View As?

Here are the exact steps we run on every model before it ships:

  1. In Power BI Desktop, open the Modeling tab and choose Manage roles. Create a role, pick the table, and write the DAX filter. Keep it short.
  2. For anything above a handful of regions, use dynamic security. Filter by the signed-in email with `[Email] = USERPRINCIPALNAME()` against a mapping table, so one role covers the whole company.
  3. On the Modeling tab, choose View As. Pick the role, and use the Other user box with a real email to preview exactly what that person will see.
  4. Publish to the service. Open the semantic model, go to Security, and add users or Entra security groups to each role.
  5. In the service, use Test as role on the same Security screen to confirm the published model behaves the same way.
  6. Check one visible total against a number you already know is correct for that person. If the grand total matches their real figure, the filter is doing its job.

Assign people through Entra security groups instead of one by one. Then membership lives in one place your IT team already manages, which keeps this piece inside your data governance structure rather than in a spreadsheet only you can find.

What does row level security not cover?

Plenty, and this is where reports leak. Row level security filters rows. It doesn't hide a column, it doesn't stop resharing, and it doesn't protect the model from someone with edit rights.

Row level security is one layer of the wider security Power BI gives you. Here is how the three main layers divide the work:

LayerWhat it controlsWhere you set it
Row level security (RLS)Which rows a person sees in a modelPower BI Desktop, Manage roles + service Security
Object level security (OLS)Which tables or columns a person can see at allTabular Editor on the model
Workspace rolesWho can view, edit, or reshare contentPower BI service workspace access

A few traps worth naming. Export to Excel respects RLS, so that path is safe. But a Member or Admin on the workspace can often open the model and see all the data, so sensitive tables need the right workspace role on top of the role filter. And object level security is a separate step in Tabular Editor, so if you need to hide a salary column, RLS alone won't do it.

How do you prove it's working with the Power BI audit log?

Setting it once and hoping is how the wrong-row incident happens. Give yourself proof.

The Power BI audit log, available through Microsoft Purview and the tenant activity events, records who viewed a report, who exported data, and who changed security on a model. Pull the ViewReport and ExportReport events once a month and confirm the list matches the people who should have access. When someone changes a role, the audit log shows it with a timestamp and a name, so a mistake has an owner and a date.

Two more habits keep this honest. Store the mapping table for dynamic security under version control, so a change to who-sees-what is reviewed like code. And run your View As check again after any model refresh that touches the security tables. Poor data quality already costs organizations an average of $12.9M a year, per Gartner, and a report that shows the wrong numbers to the wrong person is part of that bill. A ten-minute audit-log check is cheaper than rebuilding trust in a dashboard nobody opens anymore.

Frequently asked questions

### Does Power BI row level security work on the free license? The roles are defined in the model no matter which license you have. To open a shared report and have RLS applied, viewers need Pro, or the content has to sit in a Premium or Fabric capacity. Building and testing roles in Desktop is free.

### Can a user get around row level security by exporting to Excel? Export to Excel respects the filter, so the exported file only contains the rows that person is allowed to see. The real gap is edit access. Anyone with build or edit rights on the model can open it and read every row, so guard that with workspace roles.

### Why does one role show a blank report? Almost always the DAX filter matches no rows for that person, or their email is missing from the mapping table used by dynamic security. Reproduce it with View As and the Other user box, then fix the mapping row.

### How many roles should I create? Fewer roles are far easier to audit. Dynamic security with `USERPRINCIPALNAME()` and one mapping table often replaces dozens of static, hard-coded roles with a single role that scales as people join and leave.

### Does row level security slow down refresh or reports? The filter runs at query time, not during refresh, so it has no effect on your refresh schedule. Heavy role filters can slow visuals, so keep the DAX simple and test on a real data volume before you publish.
