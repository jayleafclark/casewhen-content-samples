ADLS GEN2: What It Actually Does (Plain English)

Quick answer. ADLS Gen2 is Microsoft's cloud storage built for analytics. It's Azure Blob Storage with a real folder structure, a hierarchical namespace, added on top, so tools like Synapse, Fabric, and Databricks can read huge datasets in place. It's the cheap, central lake your reports and pipelines sit on. ---

ADLS Gen2 is where your company's raw data sits before it turns into a report, and the shape of that storage decides what every dashboard above it costs. Gartner puts the average cost of poor data quality at $12.9 million a year (Gartner), and a lot of that starts in a messy lake. Get the storage right and reports get cheaper and easier to trust. Get it wrong and you pay twice, in cloud bills and in decisions made on numbers that were off.

This walkthrough covers what the service is, where the money actually goes, how it differs from plain storage, and how to keep the lake from turning into a swamp nobody can use.

What is ADLS Gen2, in plain English?

The full name gives away the whole idea: Microsoft Azure Data Lake Storage Gen2. It's Azure Blob Storage, Microsoft's cheap object storage, with one big addition: a hierarchical namespace. That's a technical term for real folders.

Plain blob storage fakes folders using prefixes in the file name. The Gen2 version gives you actual directories you can rename, move, and secure, the way folders behave on your own laptop.

Why does that matter for analytics? Big data tools scan folders all day. Renaming a folder of a million files in plain blob storage rewrites every single file name. Here that same rename is one directory operation. Multiply the difference across daily pipelines and it shows up in both speed and the bill.

Why does ADLS Gen2 cost more to query than to store?

Storing data here is close to free. The Azure list price for hot-tier storage runs around a couple of cents per gigabyte per month, and colder tiers cost even less. The real money shows up when tools read the lake.

When Microsoft Azure Synapse Analytics or Fabric runs a serverless query, you pay per terabyte scanned, roughly $5 a terabyte on the Azure price list. A wide CSV file plus a `SELECT *` reads every byte in that file. The same data stored as partitioned Parquet, which is columnar and compressed, can read a fraction of that for the identical answer.

Three habits keep the reads cheap:

  1. Store files as Parquet, not CSV. Columnar and compressed means far fewer bytes read per query.
  2. Partition folders by date, so a query for June scans the June folder and skips the rest of the year.
  3. Match the access tier to how often you read. Hot for data queried daily, cool or archive for data you keep but rarely touch.

None of this needs new tooling. It's how you lay out files and which tier you leave them on.

How is ADLS Gen2 different from plain blob storage?

Both sit on the same underlying storage account, so the price per gigabyte is similar. What you turn on is the hierarchical namespace, and that one switch changes how the storage behaves for analytics.

The short read: if a lakehouse, warehouse, or reporting tool is going to sit on this data, turn the hierarchical namespace on. If you're storing app uploads or backups, plain blob storage is fine and a touch simpler.

One catch worth knowing: the namespace setting is chosen when the account is first built, and you can't flip it later. So decide up front whether this data is headed for analytics.

How do you keep ADLS Gen2 from becoming a data swamp?

A lake with no rules fills up with files nobody can find or trust. The fix is a bit of structure, and it pays for itself fast. Remember that 94% of business spreadsheets used in decision-making contain errors (Poon et al., 2024). A governed lake is how you stop feeding those errors into every report.

Four things do most of the work:

  • Use a medallion layout. Land raw files in a bronze zone, clean and conform them into silver, and publish business-ready tables into gold. Reports read gold, so they never touch messy raw data.
  • Name and partition on a convention. Pick a folder pattern like `zone/source/table/year/month` and stick to it across the team. Predictable paths make queries cheaper and onboarding faster.
  • Set permissions at the folder level. You can grant access per directory on top of Azure role access, so finance sees finance and nobody browses the whole lake by default.
  • Turn on lifecycle rules. A policy can move files to cool or archive after a set number of days and delete what you no longer need, so storage doesn't creep up forever.

Give each zone an owner. A lake with a name on it stays usable; a lake owned by everyone gets abandoned.

Should you build on ADLS Gen2 or OneLake in 2026?

This is the live question, because Microsoft now steers new analytics work toward Microsoft Fabric, and Fabric ships with its own storage called OneLake.

OneLake is one logical lake for your whole tenant, and under the hood it runs on the same Gen2 technology. You get the lake with less to set up, plus shortcuts that point at data in your existing accounts without copying it.

So which do you pick? If you already run a lake feeding Synapse or Databricks and it does the job, keep it, and reach into it from Fabric with a shortcut when you want to. If you're starting fresh and leaning into Fabric, let OneLake be your default and skip the manual storage setup. Either way the data can stay in one place, and the same governance habits above still apply.

Frequently asked questions

Is ADLS Gen2 the same as Azure Blob Storage? Almost. It's the same blob storage running the hierarchical namespace, which adds real folders, folder-level permissions, and the read behavior that analytics tools want. You pick it when the storage account is created.

Can I convert plain blob storage to ADLS Gen2 later? Not with a switch. The hierarchical namespace is set at account creation and can't be toggled on afterward. To move existing blob data over, you copy it into a new account that has the namespace enabled.

What file format should I store in a data lake? Parquet for anything you query. It's columnar and compressed, so a serverless query reads far fewer bytes than the same data in CSV, which directly lowers your per-terabyte scan cost.

Does OneLake replace ADLS Gen2? No. OneLake is built on Gen2 and gives you a managed lake inside Microsoft Fabric. Fabric shortcuts let OneLake read your existing lake data in place, so the two work together.

Can Power BI read from ADLS Gen2? Yes. Power BI can connect to it directly, or query it through the serverless SQL pool in Azure Synapse, or read it through OneLake in Fabric.
